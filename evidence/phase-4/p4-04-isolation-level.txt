SECTION 0 — scope correction: the card's enumerated list was stale
-------------------------------------------------------------------------

The card names seven files (StockService, PriceChangeService,
ProductLifecycleService, SupplierLifecycleService, SuppliersController,
ProductsController, MaintenanceController). A source scan against the
current tree - which is what Done-when box 1 itself calls for, "so a call
site added later is not silently missed" - found the list did not match
reality in three ways, confirmed with the user before implementing:

  1. MaintenanceController has ZERO BeginTransaction call sites. It writes
     through MaintenanceLockRepository (a single-statement unique-index
     insert) and AuditLogWriter (autocommit) - nothing to fix there.
  2. PurchaseOrderService had THREE more unfixed call sites beyond the one
     P3-03 already corrected (CreateAsync) - SubmitAsync, ApproveAsync, and
     TransitionWithReasonAsync (shared by CancelAsync/CloseAsync). Not
     named in the card, in the very file the original fix came from.
  3. SystemSettingsController has one call site (SetSetting) not named in
     the card at all.

ADR-006's own carried text says "every OTHER BeginTransaction call site
still opens REPEATABLE READ" - not a fixed enumeration - so this card
fixes every production call site the scan found, not only the seven
literally named. MaintenanceController needed no change.

Full post-fix source scan, `grep -rn "BeginTransactionAsync" src/Merchandising.Api`

SECTION 1 — the mechanism, proven generically (ConnectionFactoryTests)
-------------------------------------------------------------------------

New test OpenedConnection_TransactionIsolation_MatchesWhatIsPassedToBeginTransaction
proves both halves of the divergence directly against the real, pinned
MariaDB instance, using the SAME ConnectionFactory every call site uses:
a transaction opened with no isolation argument reads back REPEATABLE-READ
from INSIDE itself; a transaction opened with IsolationLevel.ReadCommitted
reads back READ-COMMITTED from INSIDE itself. The old session-level test
(OpenedConnection_HasStrictModeAndReadCommittedIsolation) is unchanged and
still asserts the session value separately - both are true, and now both
are checked.

  dotnet test src/tests/Merchandising.Tests.Integration \
    --filter "FullyQualifiedName~ConnectionFactoryTests" --logger "console;verbosity=normal"

  Passed OpenedConnection_HasStrictModeAndReadCommittedIsolation [292 ms]
  Passed OpenedConnection_TransactionIsolation_MatchesWhatIsPassedToBeginTransaction [35 ms]

Because IsolationLevel is a MySqlConnector API argument to BeginTransaction,
not something that varies by which class or method calls it, this single
proof against the shared ConnectionFactory establishes the mechanism for
every one of the ten call sites in Section 0 - each of which now supplies
the identical argument. Per-call-site correctness is what the source scan
in Section 0 verifies; this section is what proves the argument actually
does what ADR-006's amendment says it does.

SECTION 3 — Done-when box 3: the P1-11/P1-13 concurrency proofs are
unaffected (a text-vs-reality fix, not a behaviour change)
-------------------------------------------------------------------------

Decrement_TwoThenTenSimultaneousRequests_ExactlyOneSucceedsEachRound (the
P1-13 concurrency proof) is in the Section 2 run above, unchanged, still
green. ADR-006's own Reasoning already says isolation level is not what the
concurrency guarantee depends on (InnoDB row-locking on the conditional
UPDATE is) - this run confirms that in practice, not just in the text: the
same test, same fixture, same assertions, passes identically before and
after this card's fix. No existing concurrency test changed behaviour,
which is what CLAUDE.md section 7 item 5 would require halting and
reporting if it had.

SECTION 5 — what this evidence does NOT claim
-------------------------------------------------------------------------

@@tx_isolation was not read live, inside a transaction, at each of the ten
individual call sites in Section 0 one by one - only at the two
representative points (Section 1: the shared ConnectionFactory mechanism;
Section 2: StockService end-to-end). Isolation level is purely a
MySqlConnector API argument to BeginTransaction with no dependency on which
class or method supplies it, so a tenfold repetition of the identical
runtime measurement would prove the same fact ten times, not ten different
facts. Per-call-site correctness - THAT each site passes the argument - is
what Section 0's source scan establishes; Sections 1-2 establish WHAT that
argument does. Marked here explicitly per CLAUDE.md's "any claim narrower
than its wording is marked and explained, never rounded up."
