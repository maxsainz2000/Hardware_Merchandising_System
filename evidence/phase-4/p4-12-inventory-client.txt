0. What this evidence proves, and what it deliberately does not
===============================================================================

This card's Done-when list has six boxes. Five are proven below by automated
tests plus a direct code review, run in this session. The sixth - "Login,
stock browse, receive, count, adjust and low-stock review all work against
the running API" - is NOT fully proven here, and the card is left OPEN (not
ticked done) because of it. What was and was not done, honestly:

  DONE:
    - The client builds against the real service references (no stub/mock
      transport in the shipped code - StubHttpMessageHandler exists only in
      the test project).
    - The MerchandisingApi Windows Service was confirmed Running on this
      machine (Get-Service MerchandisingApi -> Running) and the real
      integration suite (339 tests) passed against the real database in the
      same session, proving every server-side rule this client calls is
      correct.
    - Merchandising.Inventory.exe was launched directly (Start-Process) against
      that live service. It opened, its main window titled "Merchandising -
      Inventory" reported Responding=True after 4 seconds, and it was closed
      cleanly - i.e. the real client, wired to the real MerchandisingApiClient
      pointed at https://MERCH-HOST:8443/, does not crash on startup. See
      section 3.

  NOT DONE, AND WHY:
    - An authenticated click-through (sign in, then actually exercise stock
      browse / receive / count / adjust / low-stock against the live API)
      was NOT performed in this session. The seeded test accounts'
      passwords are randomly generated per installation and stored only in
      the ACL-protected C:\ProgramData\MerchandisingSystem\config\
      installation-credentials.txt (P2-11) - by design, per ADR-012
      requirement 6, nowhere in this repository. Reading that file was
      attempted and was refused by this session's own auto-mode permission
      classifier; per CLAUDE.md section 7's stop-condition rule ("if a hook
      blocks you, that is the answer... report it and stop"), that refusal
      was accepted rather than worked around.
    - This session also has no WPF GUI-automation tool (unlike claude-in-
      chrome for web pages), so even with a password, driving five tabs'
      worth of real interaction was not something this session could do
      unassisted.

  WHAT THIS MEANS FOR THE CARD: it is left OPEN. The operator (or a session
  with the installation-credentials.txt password) still owes one real,
  authenticated pass through all five tabs. Everything the automated
  evidence below CAN prove - correctness of every screen's logic against
  realistic stubbed API responses, the layout/focus-order requirement, and
  the guardrail/test posture - has been proven.

2. A known, frozen permission gap - recorded, not silently patched around
===============================================================================

PurchaseOrders.Track (needed by the Receive tab's "Load order" button, since
that is the only way to see a purchase order's lines before receiving against
them) is ProcurementAndAbove. Receiving.Confirm (needed to actually post the
receipt) is InventoryAndAbove. The two groups only overlap at Admin/SuperAdmin.

A pure "inventoryclerk" sign-in can therefore POST a receipt but cannot GET
the order first - LoadOrderAsync will come back Rejected with the API's own
403, rendered verbatim (proven by ApproveAdjustmentAsync_ForbiddenRefusalSurfacesVerbatim
in section 2 below, which exercises the identical rendering path for a
different 403). Only admin/superadmin can complete the Receive tab
end-to-end today.

This is a Phase 2 role-matrix property, and Phase 2 is frozen (tasks.md's
Phase 4 entry note: "no phase below may re-litigate a Phase 2... decision").
This card does not change PolicyRegistry. It is recorded here as a real,
open question for whoever plans past Phase 4: should Inventory Clerk also
hold PurchaseOrders.Track (read-only), or is receiving meant to be an
Admin-mediated action in this system's design? Not decided by this card.
