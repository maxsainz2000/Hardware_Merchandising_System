Root cause: StockDecrementTests, ProductLifecycleTests, and
AuthorizationMatrixTests each reuse ONE fixed fixture product across every
integration-test run ever executed, and their <TestInitialize> setup reset
StockBalances.Quantity directly (a bare UPDATE, or an initial INSERT of a
nonzero baseline) to a known starting value before each run.
StockMovements is append-only, so every historical decrement from every
past run stayed in the ledger forever, while the balance was repeatedly
force-reset to the baseline outside of any movement - the two have been
silently diverging since Phase 1. This is exactly the class of bug
plan.md section 7 wrote this card to catch before Phase 7: "Ledger drift
found in Phase 7 is a nightmare; found automatically in Phase 4 it is a
small bug."

Reported to the user; decision was "fix fixtures + heal now" (see
conversation). Two changes follow.

-------------------------------------------------------------------------
SECTION 2 — fix: fixture helpers now write a compensating movement
-------------------------------------------------------------------------

Three helpers, in three already-gated Phase 1/2 test files, changed to
write a compensating StockMovements row in the SAME transaction as any
direct balance change, and their initial fixture-creation INSERTs changed
to start every product at Quantity = 0.000 (matching zero movements)
instead of a nonzero baseline with no movement behind it:

  - StockDecrementTests.ResetStockBalanceAsync
    + StockDecrementTests.EnsureFixtureProductAsync / EnsureConcurrencyFixtureProductAsync
  - ProductLifecycleTests.ResetStockBalanceDirectlyAsync
  - AuthorizationMatrixTests.ResetStockBalanceDirectlyAsync
    + AuthorizationMatrixTests.EnsureFixtureProductAsync

None of these touch, edit, or delete any existing StockMovements or
AuditLogs row (CLAUDE.md section 5 / section 7 stop condition 7) - each
only ever INSERTs a new row alongside the balance write it already made,
inside the same transaction, the same shape every real stock-changing
command already follows.

Reviewed every existing assertion that reads StockMovements for these
fixtures to confirm the extra "Test fixture balance reset (...)" movement
row cannot break it: StockDecrementTests filters by the test's own
correlation ID or takes the newest row by Id (the reset always runs before
the test's own decrement); ProductLifecycleTests only asserts COUNT(*) > 0.
Neither depends on an exact row count.
