$ mysql -u root merchandising -e "SHOW CREATE TABLE Receipts\G"

CREATE TABLE `receipts` (
  `Id` int(11) NOT NULL AUTO_INCREMENT,
  `PurchaseOrderId` int(11) NOT NULL,
  `ReceivedByUserId` int(11) NOT NULL,
  `ReceivedAtUtc` datetime(6) NOT NULL,
  `ReferenceNumber` varchar(50) NOT NULL,
  `CreatedAtUtc` datetime(6) NOT NULL,
  PRIMARY KEY (`Id`),
  UNIQUE KEY `UQ_Receipts_ReferenceNumber` (`ReferenceNumber`),
  KEY `FK_Receipts_PurchaseOrders` (`PurchaseOrderId`),
  KEY `FK_Receipts_ReceivedBy` (`ReceivedByUserId`),
  KEY `IX_Receipts_ReceivedAtUtc` (`ReceivedAtUtc`),
  CONSTRAINT `FK_Receipts_PurchaseOrders` FOREIGN KEY (`PurchaseOrderId`) REFERENCES `purchaseorders` (`Id`),
  CONSTRAINT `FK_Receipts_ReceivedBy` FOREIGN KEY (`ReceivedByUserId`) REFERENCES `users` (`Id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci

  [PASS] no RowVersion, no UpdatedAtUtc - Receipts is immutable once written,
         the same shape 0001 gives StockMovements/AuditLogs, argued in the
         migration's own header. ReferenceNumber is UNIQUE, distinct from the
         ADR-007 idempotency key stored separately in IdempotencyKeys.

  CONSTRAINT `CK_PurchaseReturnLines_Cost` CHECK (`Cost` >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci

  [PASS] RemovesStock is spec section 10.1's "whether stock is removed",
         TINYINT(1) matching the established boolean convention (0001,
         0007). No database CHECK bounds QuantityReturned against "received
         quantity less prior returns" - that bound is an aggregate over
         every prior sibling row, which a MariaDB CHECK cannot express, and
         is P4-08's job at the API, computed from committed rows, exactly as
         that card's own text states.

  [PASS] every table states COLLATE utf8mb4_unicode_ci explicitly (ADR-003);
         money DECIMAL(19,4), quantities DECIMAL(19,3) (ADR-004), no
         floating-point type anywhere.

===============================================================================
6. What this card did NOT do
===============================================================================

No controller, no repository, no contract type, no client, no Domain enum
for return statuses. P4-05 builds the first receiving endpoint and P4-08 the
first purchase-return endpoint; until they exist, nothing in the running API
reads or writes any of these four tables.

The P2-03 authorization matrix suite is NOT extended by this card and its
count is unchanged - the same note P3-02's evidence makes for the same
reason: no route is added here, so there is no policy cell to assert.

No self-approval rule is decided for PurchaseReturns.ApprovedByUserId. The
column exists so that decision costs no new migration when P4-08 makes it;
it is not decided here by accident.
