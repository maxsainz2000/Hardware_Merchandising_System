===============================================================================
A real bug caught while building this, worth recording
===============================================================================
ProductLifecycleService.SetActiveStateAsync originally read the "already in
this state" product (to distinguish NoChange from ProductNotFound) BEFORE
rolling back the open-but-now-empty transaction. MySqlConnector refused
that read outright: "The transaction associated with this command is not
the connection's active transaction" (InvalidOperationException), because
ProductRepository.GetByIdAsync's SELECT never attaches the caller's
transaction. DeactivateThenReactivate_ThroughHttp_BothSucceed caught this
immediately as a 500 on the second (already-inactive) deactivate attempt,
not as a design defect - the fix was reordering: RollbackAsync +
DisposeAsync the transaction first, then read plainly. Recorded because it
is the same class of "which order these two calls happen in matters" lesson
ADR-017's own header records for a different bug.
