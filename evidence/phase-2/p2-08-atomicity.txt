P2-08 - forced-failure atomicity proof, P1-12 shape - evidence
Captured 2026-08-25, against the real pinned MariaDB instance (10.4.32-MariaDB
via XAMPP 8.2.12-0), Debug configuration (the #If DEBUG-gated fault-injection
seam is compiled out of Release entirely - see PriceChangeService.vb's own
header, identical mechanism to Inventory.StockService's P1-12 seam).

Mechanism: PriceChangeService.ChangePriceAsync takes an optional
testOnlyFaultAfterAuditInsert delegate. By the point it is invoked, the
Products UPDATE, the PriceHistory INSERT, and the AuditLogs INSERT have all
already been sent to the server - still uncommitted, inside one open
transaction. Throwing there and letting the exception propagate out of
ChangePriceAsync (never caught inside the method - see its header) is the
proof: the enclosing `Using connection` block's Dispose() severs the
connection on the way out, and MariaDB rolls back whatever transaction was
still open on that connection. No explicit RollbackAsync call is exercised
by this path - the proof is that an ordinary connection drop is enough,
exactly as ADR-006's Reasoning section commits to.

Test: ChangePriceAsync_FaultInjectedBeforeCommit_RollsBackProductPriceHistoryAndAuditRows
(src/tests/Merchandising.Tests.Integration/PriceChangeTests.vb). Fixture
product's Price is reset to the known baseline (10.0000) before the test;
before/after counts for Products.Price, PriceHistory rows (scoped to this
attempt's own fresh CorrelationId), and AuditLogs rows (same CorrelationId)
are all read and compared.

SUMMARY

Done-when box 1 (all three effects commit together or not at all, proven by
a forced-failure test in the shape of P1-12): PASS. Products, PriceHistory,
and AuditLogs all rolled back together from one injected fault, the same
connection-drop mechanism ADR-006 already relies on for the stock decrement
- no new atomicity mechanism was invented for this card, the frozen pattern
was reused exactly as the task card asked.
