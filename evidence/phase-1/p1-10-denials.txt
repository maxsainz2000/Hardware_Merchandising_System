--- AFTER: the same request against the fixed build ---

    HTTP 400
    {"errorCode":"INVALID_CORRELATION_ID","message":"The supplied correlation ID
     header is not valid.","correlationId":"2e6323ad-4566-47b0-b5b9-4fe839331c3b",
     "errors":{"X-Correlation-Id":["Must be a UUID in the canonical 36-character
     form, ... Omit the header entirely to have one assigned."]}}

Two changes produced that, and they are independent layers:

  1. CorrelationIdMiddleware now requires a canonical 36-character UUID and
     refuses anything else with a controlled 400 BEFORE the value can be bound
     as a SQL parameter. This closes the specific path.
  2. ExceptionHandlingMiddleware, registered OUTERMOST, converts any unhandled
     exception into the standard envelope and logs the original server-side.
     This closes the general case - the next unanticipated exception, whatever
     throws it, cannot leak either.

Layer 2 is the one that matters for the future. Layer 1 alone would have fixed
this bug and left the class of bug open.

WHAT THIS FILE DOES NOT PROVE
===============================================================================

1. AN END-TO-END 500 THROUGH THE LIVE PIPELINE.
   PART A shows a real unhandled MySqlException converted from a leak into a
   controlled response, which is the strongest available evidence, but it works
   by removing the fix rather than by inducing a fault against the fixed build.
   Driving an arbitrary unhandled exception through a RUNNING API needs the
   test-only fault-injection seam that P1-12 owns, plus P1-19's
   WebApplicationFactory wiring. Until then the general case rests on
   ExceptionHandlingMiddlewareTests, which exercises the real middleware with
   real ASP.NET Core types.

   Consequence for the developer-exception-page claim: it is proven that the
   handler handles rather than propagates, and therefore that the developer page
   has nothing left to format. It is NOT proven by observing a live 500 in
   Development.

2. CRLF HEADER INJECTION, LIVE. Covered by
   CorrelationIdMiddlewareTests.CorrelationIdContainingCrLf_..., not by an HTTP
   capture: the client library refuses to transmit a header value containing
   CR/LF, so the request cannot leave the machine to be tested end to end.

FINDING RAISED BY THIS RUN, OUTSIDE THIS CARD'S BOXES
===============================================================================

MERCH-HOST RESOLVES TO A STALE ADDRESS ON THIS NETWORK.

    Resolve-DnsName MERCH-HOST  ->  192.168.100.165
    this host's actual LAN IPv4 ->  192.168.100.123

The hosts-file entry recorded as verified at P1-09 ("Resolve-DnsName MERCH-HOST
resolves and replies") is no longer true: the lease moved. Connecting to
https://MERCH-HOST:8443 from this machine now times out against an address that
is either unused or belongs to some other device on the LAN.

This is the DHCP trap this project has already been bitten by once and wrote
down (P0-05, evidence/phase-0/host-ip-reservation.txt section 2). It changes
nothing about the "never configure a host by manual static IP" conclusion - the
fix is still an address fixed on network equipment we control, per ADR-012 - but
it does mean:

  - P1-09's hosts-file note should not be read as a standing guarantee. It was
    true on the network the machine sat on that day.
  - Any future run that needs the NAME to work must re-check resolution first
    and correct the hosts entry (elevation required) before concluding anything
    about certificates or trust.

Not fixed here: correcting the hosts file needs an elevated session, the same
gap that leaves P1-09's firewall box open. Both should be done in one elevated
sitting.
