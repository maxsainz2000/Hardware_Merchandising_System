=== 2. Why an API-side guard is required: the database rounds over-scale values silently ===
$ mysql -u merch_api merchandising -e "UPDATE products SET Cost = 0.19995 WHERE Sku='PROOF-SKU'; SHOW WARNINGS; SELECT Cost FROM products WHERE Sku='PROOF-SKU';"
Level  Code  Message
Note   1265  Data truncated for column 'Cost' at row 1
Cost
0.2000
  Confirms ADR-004.1: STRICT_TRANS_TABLES does not turn an over-scale
  decimal into an error. 0.19995 (5 dp) into DECIMAL(19,4) silently becomes
  0.2000 - a Note, not an ERROR, and INSERT/UPDATE reports success either
  way. A value read back at the correct scale proves nothing about whether
  it arrived pre-rounded or was rounded by the server.

Proof rows (products/stockbalances 'PROOF-SKU', the auditlogs and users rows
from p1-07-audit-immutability.txt section 5) were deleted afterward as
merch_migrator (merch_api has no DELETE on products/stockbalances/users/
auditlogs by design - 0002's comment: "deactivate, do not delete"). Table
row counts confirmed back at 0 for all proof data; roles (5, seeded by the
migration) and the real schemamigrations row are the only permanent rows
left, per p1-07-audit-immutability.txt section 5.

=== 3. Client-supplied over-scale values are validated, not rounded, at the API boundary ===
This is the acceptance box's actual requirement - proven not by reading a
stored value back (section 2 shows exactly why that proves nothing), but by
exercising the guard directly: Merchandising.Domain.DecimalScaleGuard,
src/tests/Merchandising.Tests.Unit/DecimalScaleGuardTests.vb.

Judgment call: written as a unit test, not a Tests.Integration test, despite
the card's literal wording "Integration test". DecimalScaleGuard is pure
Domain logic with no I/O - ADR-009's own project split assigns "domain and
calculation tests" to Merchandising.Tests.Unit and reserves
Merchandising.Tests.Integration for tests that need the real MariaDB
instance. Giving this test a database dependency it does not need would
contradict that split for no benefit.
