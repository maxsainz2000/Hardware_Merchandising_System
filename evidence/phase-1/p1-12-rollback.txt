Server    : 10.4.32-MariaDB
Fixture   : Sku=p1_11_fixture_sku, Id=2 (same permanent fixture P1-11 uses -
            Products/StockBalances have no DELETE grant for merch_api).
Mechanism : Merchandising.Api.Inventory.StockService.DecrementAsync now takes
            an Optional Action parameter, testOnlyFaultAfterAuditInsert,
            invoked immediately after the AuditLogs insert and immediately
            before transaction.CommitAsync - i.e. after BOTH the
            StockMovements and AuditLogs rows are sent to the server, still
            uncommitted. This is the superset of the card's "after the
            movement insert but before commit" window, and the strongest
            point available: proving rollback here proves it for every row
            this method ever writes. The exception is deliberately NOT
            caught (see StockService.vb's own header comment) - it
            propagates out through the enclosing `Using connection` block,
            whose Dispose() severs the connection, and MariaDB rolls back
            whatever was still open on that connection.

PART C - box 3: the same fault cannot be enabled in a Release build
===============================================================================

VB's preprocessor cannot interrupt a comma-continued parameter list (tried
first; confirmed as a hard compile error - BC30203/BC30013), so
testOnlyFaultAfterAuditInsert is present in the method signature in every
configuration. What makes it inert in Release is that its ONLY call site is
wrapped in `#If DEBUG ... #End If` (StockService.vb, immediately before
CommitAsync) - a Release build's compiled DecrementAsync never invokes the
delegate, regardless of what a caller passes. Proven empirically, not just
by reading the source:

$ dotnet build src/tests/Merchandising.Tests.Integration/Merchandising.Tests.Integration.vbproj --configuration Release --nologo
Build succeeded. 0 Warning(s), 0 Error(s). (Api, Infrastructure, Domain, Contracts, Maintenance all rebuilt Release too.)

$ dotnet test src/tests/Merchandising.Tests.Integration/Merchandising.Tests.Integration.vbproj --configuration Release --no-build --nologo --filter "FullyQualifiedName~Decrement_FaultInjectedBeforeCommit" --logger "console;verbosity=detailed"

This failure IS the proof, not a defect: under Release, the same throwing
delegate that rolls the transaction back under Debug is never invoked at
all, so DecrementAsync runs to completion and commits normally - which is
exactly why the test's own "an exception must have been thrown" assertion
fails. `run-tests.ps1` never builds or runs this project in Release
configuration (its $Configuration parameter defaults to 'Debug'), so this
Release-only behaviour never gates the normal test pass/fail signal.
