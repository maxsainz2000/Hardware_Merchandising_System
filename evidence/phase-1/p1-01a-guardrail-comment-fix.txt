WHAT THIS FIXES

  Found at P1-01. G-B and G-D matched raw project-file text, so they could
  not distinguish a real reference or build property from the rule written
  down in an XML comment. Writing "never reference <the connector>" inside
  Merchandising.ClientCommon.vbproj FAILED THE BUILD - the guardrail read its
  own prohibition as a violation. The client project file is the single best
  place to record why that rule exists, and it was the one place it could not
  be recorded.

WHY IGNORING COMMENTS IS SAFE FOR G-B AND G-D

  Both look for things that must TAKE EFFECT to matter: a ProjectReference, a
  PackageReference, a PublishAot property. MSBuild never sees anything inside
  a comment, so a commented violation is not a violation. There is no evasion
  route to close here - only false positives to remove. Cases 2, 3 and 5 below
  prove the real violations are still caught.

WHY G-C DELIBERATELY STILL SCANS COMMENTS

  G-C looks for credentials. A connection string in a comment is a real
  leaked credential: it is in the working tree, it is in the history, and it
  is readable by anyone with a clone. Case 7 proves this asymmetry holds.

METHOD

  Every case mutates a real project file, runs the guardrail for real through
  pwsh, and judges on the actual exit code. The file is restored in a finally
  block; cases 1 and 8 bracket the run to prove the repository was clean
  before and is clean after.
