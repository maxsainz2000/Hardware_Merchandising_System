  compensating property to make that work.

  NOTE WHAT IS NOT PRESENT:

    - No PackageReference of any kind. ASP.NET Core arrives through the
      Web SDK's implicit framework reference. The API currently needs zero
      NuGet packages, so there is nothing here to pin in docs/adr.md yet.
    - No appsettings.json, no Properties/launchSettings.json. Runtime
      config comes from an ACL-protected host location at P1-05; Kestrel
      endpoints and HTTPS are P1-09. No development URL is committed.
    - No EnableRequestDelegateGenerator / PublishAot / PublishTrimmed.
      See section 3 - their absence is the point.

3  INHERITANCE PROOF - EnableRequestDelegateGenerator AND FRIENDS
---------------------------------------------------------------------------

  The Done-when box reads: "EnableRequestDelegateGenerator=false INHERITED
  from Directory.Build.props". Inherited is the operative word. Restating
  the property in Merchandising.Api.vbproj would have satisfied a naive
  reading of that box while proving the opposite of what it asks - only
  that this file is capable of setting the property itself.

  So it is deliberately NOT set locally, and the proof is done in two
  halves: evaluate the property against the project, then show the project
  file does not set it.

  HALF ONE - evaluate the property MSBuild actually resolved:

  $ dotnet msbuild src\Merchandising.Api\Merchandising.Api.vbproj \
        -getProperty:<name> -nologo

    EnableRequestDelegateGenerator     = false     <- the box
    PublishAot                         = false
    PublishTrimmed                     = false
    OptionStrict                       = On
    OptionExplicit                     = On
    OptionCompare                      = Binary
    OutputType                         = Exe
    TargetFramework                    = net10.0
    UsingMicrosoftNETSdkWeb            = true      <- Web SDK confirmed

  HALF TWO - the project file does not set any of them:

  $ Select-String -Path <the .vbproj> -Pattern
        'EnableRequestDelegateGenerator|PublishAot|PublishTrimmed|OptionStrict'

    line 30: NO EnableRequestDelegateGenerator, PublishAot OR PublishTrimmed.

  ONE match, and it is the sentence inside the comment block explaining
  why they are absent. Nothing sets them here. The values above therefore
  came from Directory.Build.props and nowhere else.

  Note that UsingMicrosoftNETSdkWeb=true is read from the resolved SDK,
  not from the Sdk attribute string. It confirms the Web SDK genuinely
  loaded, rather than confirming that the file says it should.

  ALSO CONFIRMED BY THE SAME QUERY: TargetFramework resolved to net10.0
  from the $(MerchNetTfm) variable, and OptionStrict/Explicit/Compare came
  through as On/On/Binary. The P1-01 rule that no .vbproj may hard-code a
  TFM still holds after the conversion.

8  ONE THING DID GO WRONG - AND IT WAS NOT RUNG A
---------------------------------------------------------------------------

  THE FIRST BUILD FAILED. Recording it because "0 warnings first try" is
  only a useful claim if the failures are recorded too, and because the
  failure is a repeat of a defect this repository has already been bitten
  by twice.

  $ dotnet build src\Merchandising.Api\Merchandising.Api.vbproj -v minimal

    Merchandising.Api.vbproj(26,5): error MSB4025: The project file could
    not be loaded. An XML comment cannot contain '--', and '-' cannot be
    the last character. Line 26, position 5.
    EXIT CODE: 1

  CAUSE. The comment block used rules of hyphens as section separators.
  A run of hyphens is illegal inside an XML comment, so MSBuild rejected
  the file before the Visual Basic compiler was ever invoked.

  WHY IT IS NOT RUNG A FRICTION, AND MUST NOT BE LOGGED AS SUCH. It has
  nothing to do with the Web SDK, ASP.NET Core, or Visual Basic. The same
  file would have failed identically on Sdk="Microsoft.NET.Sdk", and it
  failed at XML parse time - before SDK resolution, before restore, before
  compilation. Counting it as friction would have triggered the P1-02a
  insurance spike against a fallback there is no reason to need, on the
  strength of a typo in a comment. ADR-001 records it in the same terms.

  WHY IT MATTERS ANYWAY. This is the THIRD time this exact defect has hit
  the repository. P1-01 found it in Directory.Build.props, where it had
  made every MSBuild invocation fail and had survived the whole of Phase 0
  undetected, then reintroduced it twice while fixing it. The lesson from
  P1-01 was written down in that file's own comment - and it still did not
  prevent a fresh occurrence in a new file, because the warning lived only
  where the bug had previously been.

  FIX. Separators changed to equals signs, and the reason recorded in the
  project file itself so the next person to edit a comment block there
  reads it before repeating it a fourth time.

  Corrected file parsed and built on the next attempt: 0 warnings,
  0 errors, EXIT 0 (section 4).
