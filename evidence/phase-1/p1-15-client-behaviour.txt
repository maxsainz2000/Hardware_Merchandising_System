=============================================================================
THE DESIGN DECISION G-26 ACTUALLY TURNS ON
=============================================================================

G-26 reads: "Offline behavior was not sufficiently explicit → make
online-only status visible; reject writes when API unavailable; do not
queue unverified transactions."

The mistake that gap describes is not "no offline indicator". It is
treating every failure as the same failure. So the client distinguishes:

    The API answered with an error       -> Rejected, state stays Online
    The API was never reached            -> Unavailable, state Unavailable

Collapsing those would mean a 409 InsufficientStock renders as "you are
offline", sending an operator to check the network cable over a business
rule. It would also mean the reverse: a genuine outage rendered as a server
error, inviting a retry of a write whose fate is unknown.

Every unavailable-state test below is therefore PAIRED with a control that
reaches a server and is refused by it. Without the pair, a client that
reported "offline" for everything would pass the suite.

No retry policy. No outbox. No local queue. Their ABSENCE is the feature —
there is no code to disable, so there is nothing to regress.

-----------------------------------------------------------------------------
BOX 2 — connection-unavailable state
-----------------------------------------------------------------------------

ApiUnreachable_ProducesUnavailableStateAndAPlainMessage
    Signs in successfully (state -> Online), then the transport starts
    throwing the exception Windows raises when nothing is listening
    (HttpRequestException wrapping SocketError.ConnectionRefused).
    Asserts: Outcome = Unavailable, State = Unavailable, Value is Nothing,
    and the message names the cause ("...The API is not running.") rather
    than being generic.

ServerRefusal_IsReportedAsRejectedAndStaysOnline           [the control]
    Same client, but the server answers HTTP 409 with the ADR-014 error
    envelope. Asserts: Outcome = Rejected, State stays ONLINE, error code
    INSUFFICIENT_STOCK preserved, correlation ID present.

    This pair is the actual proof. The first test alone would pass for a
    client that called everything an outage.

ConnectionState_BeforeAnyCall_IsUnknownRatherThanOnline
    A fresh client reports Unknown, not Online. "No evidence either way"
    must not render as a green light.

-----------------------------------------------------------------------------
BOX 3 — refuses to queue or fake the write  (the heart of G-26)
-----------------------------------------------------------------------------

UnreachableWrite_IsNeverQueuedOrReplayedAfterRecovery
    1. Sign in while the API is up.
    2. API goes down. Decrement -> Unavailable.
    3. API comes back. A DIFFERENT call (/auth/me) succeeds, so the client
       has demonstrably noticed the recovery and had every opportunity to
       flush a queue.
    4. Assert: exactly ONE request to /stock/decrement was ever put on the
       wire, across the whole sequence.

    Step 3 is what makes this a real test. Asserting "no retry" while the
    client still believes it is offline would prove nothing.

ProtectedCallWithoutToken_IsRefusedLocallyAndNeverSent
    A protected call with no token is refused before the wire: zero
    requests recorded by the transport, and the connection state stays
    Unknown — nothing was learned about the server, so nothing is claimed
    about it.

-----------------------------------------------------------------------------
BOX 4 — token never written to disk
-----------------------------------------------------------------------------

SignIn_WritesTheTokenNowhereOnDisk
    Empirical, not by inspection. The login returns a distinctive fixture
    token; every file created or modified during the sign-in is then read
    back and searched for that exact string.

    Searched in full:      the application directory
                           %LOCALAPPDATA%\MerchandisingSystem
                           %APPDATA%\MerchandisingSystem
                           %ProgramData%\MerchandisingSystem
                           %LOCALAPPDATA%\IsolatedStorage
    Searched one level:    %LOCALAPPDATA%, %APPDATA%, %TEMP%

    Result: 0 files contained the token.

    HONEST LIMIT: this is a targeted sweep, not a whole-disk proof. An
    earlier version recursed all of AppData and turned a millisecond test
    into a multi-minute one; a test slow enough to be skipped proves less
    than a fast one that actually runs. It covers every location this
    application could plausibly persist to, and it fails loudly if someone
    later adds a settings file, a session cache, or a log line that
    helpfully includes the token.

Dispose_DiscardsTheHeldToken
    A disposed client no longer holds a credential.

-----------------------------------------------------------------------------
CORRELATION-ID PROPAGATION (a named deliverable, not its own box)
-----------------------------------------------------------------------------

EveryRequest_CarriesItsOwnCanonicalCorrelationId
    Every request carries X-Correlation-Id in canonical "D" form, and two
    calls never share one. ADR-014 has the API reject any other shape with
    a controlled 400, so this format is a contract rather than a style
    choice — P1-10 found that path the hard way.

AfterSignIn_ProtectedCallsCarryTheBearerToken
    Protected calls carry "Bearer <token>" (the Session scheme, ADR-005);
    the login call itself carries no Authorization header.

NOTES FOR WHOEVER RUNS THE CROSS-MACHINE PASS
=============================================================================

1. Correct the hosts entry on the host first. MERCH-HOST is stale.
2. Apply the P1-09 firewall rule — scripts/configure-firewall-dev.ps1 has
   never been run, so TCP 8443 is not open. Note that two Windows
   auto-prompt rules DO exist for the debug binary:

       TCP/UDP "Query User{...}merchandising.api.exe"
       Action Allow, Profile Private, Port Any, Remote Any

   Those are far wider than the intended rule and were created by clicking
   Allow on a Windows prompt, not by the script. A second machine could
   connect through them and prove nothing about the intended scoping.
   Decide whether to remove them before treating a cross-machine pass as
   evidence of the firewall design.
3. Trust the certificate on the client per docs/installation-guide.md §4 /
   evidence/phase-1/p1-09-client-trust-steps.md.
4. Seed something to decrement:

       Merchandising.Maintenance.exe create-user clerk <password> InventoryClerk
       Merchandising.Maintenance.exe seed-demo clerk

   seed-demo posts the opening balance as a MOVEMENT (conditional update +
   StockMovements + AuditLogs, one transaction, affected rows verified),
   not as a direct write to StockBalances. A seed that bypassed the ledger
   would leave a balance no movement explains.
5. The client machine needs the .NET 10 Desktop Runtime 10.0.9 x64 and
   must NOT have the SDK. A machine with the SDK cannot prove box 1.
