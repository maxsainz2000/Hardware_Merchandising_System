Spec §11 · Closes G-13 · Decides ADR-007 (PENDING -> ACCEPTED by this evidence)

DESIGN, AS IMPLEMENTED
=============================================================================

ADR-007's decision: IdempotencyKeys table, unique on (Scope, KeyValue).
Insert-first strategy - the command claims its key before doing work, and
the committed response payload is stored and replayed verbatim on repeat.

The table and merch_api's INSERT/UPDATE/DELETE grant on it already existed
(migration 0001_foundation.sql, grants 0002) - this card is application code
against StockService.DecrementAsync, the only transactional command that
exists in this phase (Phase 1 scope discipline).

Mechanism (Merchandising.Infrastructure.Data.IdempotencyStore,
Merchandising.Api.Inventory.StockService):

  1. TryClaimAsync INSERTs (Scope='Inventory.StockDecrement', KeyValue=key)
     as the FIRST statement inside the same transaction as the balance
     decrement / movement / audit writes.
  2. Claim succeeds -> proceed exactly as P1-11/12/13 already do. Before
     commit, CompleteAsync UPDATEs that same row's ResponsePayload
     (reflection-based System.Text.Json.JsonSerializer - source generation
     is C#-only) and CompletedAtUtc, in the same transaction. Claim,
     movement, audit row, and stored response commit together or not at
     all.
  3. Claim fails with a duplicate-key error -> another transaction already
     holds this key. MariaDB locks the unique-index entry at INSERT time,
     before commit, so a genuinely concurrent second INSERT BLOCKS on that
     lock and only resolves once the first transaction commits or rolls
     back - this is the same row-locking mechanism ADR-006/P1-13 already
     proved for StockRepository.TryDecrementAsync's conditional UPDATE, not
     a fresh assumption. By the time the duplicate-key error is observed,
     the winner has committed (a rolled-back winner releases the lock and
     the row never existed to collide with). Roll back the local no-op
     transaction, read the winner's stored payload back (visible under
     READ COMMITTED, ADR-006), and replay it verbatim.
  4. Because the claim lives in the same transaction as everything else, an
     InsufficientStock rollback also rolls back the claim - a key from a
     failed attempt is free for a legitimate retry with no separate
     expiry/cleanup code.

DONE-WHEN BOXES, MAPPED TO TESTS (StockDecrementTests.vb)
=============================================================================

Box 1 "The same key sent five times produces one movement and five
identical responses":
  Decrement_SameIdempotencyKeyFiveTimes_CreatesOneMovementAndFiveIdenticalResponses
  - five sequential calls, one idempotencyKey, each with its own fresh
    correlationId (as five separate HTTP retries would send) - asserts all
    five responses carry the ORIGINAL correlationId (proving replay, not
    recomputation), one StockMovements row, one IdempotencyKeys row, and
    the balance moved exactly once.

Box 2 "A different key produces a second movement":
  Decrement_DifferentIdempotencyKeys_CreatesTwoIndependentMovements
  - two distinct keys -> two distinct movement Ids, balance decremented
    twice.

Box 3 "Concurrent requests with the same key produce one movement":
  Decrement_ConcurrentRequestsSameIdempotencyKey_ProduceExactlyOneMovement
  - 10 calls fired without awaiting any individually (same pattern P1-13
    used for real concurrency), all sharing one idempotencyKey. Every one
    of the 10 succeeds (a losing claim replays, it does not error) and all
    10 report the same movement Id. Raw distribution captured below, not
    just pass/fail.

Box 4 "A key from a failed command does not block a legitimate retry":
  Decrement_IdempotencyKeyFromInsufficientStock_DoesNotBlockLegitimateRetry
  - same key used first on an over-large (InsufficientStock) request, then
    reused on a valid one. The retry succeeds, is a genuine new command
    (its own correlationId, not a replay of the failed attempt), and
    exactly one IdempotencyKeys row exists afterwards for the key - the
    failed attempt's claim did not linger.

Note on the box-3 evidence: all 10 concurrent attempts report movementId=73
- the same movement, confirming exactly one of the 10 actually performed the
decrement and the other 9 replayed its stored response rather than each
attempting (and being individually rejected for) their own decrement. This
is the qualitative difference from P1-13's distribution immediately above
it in this same run: P1-13's 9 losers are InsufficientStock (an error
outcome, by design - two DIFFERENT commands racing for the same unit of
stock); P1-14's 9 losers are Success (not an error - the SAME command,
replayed). Placing both distributions side by side in one evidence file is
deliberate: it is the clearest way to show the two mechanisms are related
(same row-locking primitive) but produce opposite-looking outcomes on
purpose.
