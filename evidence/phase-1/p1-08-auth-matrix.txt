===============================================================================
BUG FOUND BY THE FAILING TEST - UserRepository.RecordFailedLoginAsync
===============================================================================

The very first run of Login_SixBadPasswords_LocksAccountAndLogsIt failed for
the RIGHT reason, exactly as the task loop asks a failing-test-first step to:

  Assert.AreEqual failed. Expected:<InvalidCredentials>. Actual:<Locked>.
  Attempt 4 should not lock the account yet.

Root cause: the original single UPDATE statement was

    SET FailedLoginAttempts = FailedLoginAttempts + 1,
        LockedUntilUtc = CASE WHEN FailedLoginAttempts + 1 >= @maxAttempts ...

MariaDB evaluates a single-table UPDATE's SET assignments left to right, and
a later assignment that reads a column already reassigned earlier in the
SAME statement sees the NEW value, not the pre-update one. Because
FailedLoginAttempts was reassigned first, the CASE's own "FailedLoginAttempts
+ 1" read the just-incremented value - effectively comparing (old+1)+1 to the
threshold - and locked the account one attempt early, at 4 instead of 5.

Confirmed directly against the database after the failing run:

  Username              FailedLoginAttempts  LockedUntilUtc
  p1_08_fixture_lockout  4                    2026-08-19 01:27:42.127463

Fix: reorder the SET list so LockedUntilUtc's CASE is computed BEFORE
FailedLoginAttempts is reassigned, so it reads the true pre-update count.
See UserRepository.vb's RecordFailedLoginAsync XML doc remarks for the
in-code explanation of why the ordering is load-bearing, not cosmetic.

After the fix: 15/15 integration tests pass, confirmed on two independent
runs (repeatability), and independently confirmed live over HTTP in PART B
above - attempts 1-4 return 401, attempt 5 returns 423 and locks, attempt 6
(and a subsequent correct-password attempt, case 14) both stay 423.

NOTE - correlation-Id length is now a live boundary condition
===============================================================================

AuditLogs.CorrelationId is CHAR(36) NOT NULL (db/migrations/0001_foundation.sql).
CorrelationIdMiddleware accepts whatever the caller sends in X-Correlation-Id
verbatim (case 11 above proves the round trip) and AuditLogWriter binds it
straight into that column with no length check. A caller sending a
correlation Id longer than 36 characters would currently hit MariaDB's
strict-mode ERROR 1406 on the audit INSERT (STRICT_TRANS_TABLES, ADR-003.2)
rather than a controlled 400. Not exercised by this card's acceptance matrix
- flagged here for whichever later task hardens general request validation,
since P1-08's own scope is authentication, not input-length validation on a
header no client in Phase 1 sets to an attacker-chosen value yet.
