P1-11  ATOMIC STOCK DECREMENT - DECIMAL SCALE (ADR-004.1)
Done-when box 5: a decrement whose computed value exceeds storage scale
(quantity >3 dp) is rejected before insert. StockBalances.Quantity is
DECIMAL(19,3) (ADR-004); the value tested here has 4 decimal places.

Judgment call, same one P1-07 made for DecimalScaleGuard and recorded in
p1-07-precision-check.txt section 3: the guard is exercised in TWO places
here, not one -

  1. An "Integration test" against the real database (the card's own
     wording), proving the precondition holds at the StockService method
     itself - StockDecrementTests.Decrement_OverScaleQuantity_
     RejectedBeforeAnyRowWritten (PART A below).
  2. A live HTTP call through InventoryController, proving the same
     rejection happens at the actual API boundary a real client crosses,
     with the field-level 400 body ADR-004.1 requires (PART B below).

Server : 10.4.32-MariaDB
API    : same live process as the other two P1-11 evidence files.

===============================================================================
WHY THIS IS NOT THE SAME AS "A CORRECTLY-SCALED VALUE WAS STORED"
===============================================================================
Per ADR-004.1's own warning, a stored value at the right scale proves
nothing on its own - the server rounds silently either way. What this file
proves instead is that 1.9999 never became a bound parameter in the first
place: PART A shows the guard throws before StockRepository is ever called,
and PART B shows the same rejection surfaces to a real caller as a 400 with
field-level detail, not a 200 carrying a quietly-rounded number.

SUMMARY
===============================================================================
Box 5: PASS. Proven at both the method boundary (PART A, real database,
"Integration test" per the card's literal wording) and the HTTP boundary
(PART B, the shape a real client actually experiences).
