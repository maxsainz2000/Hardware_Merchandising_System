Done-when boxes: 1 (exactly one request succeeds), 2 (all others receive a
controlled conflict/insufficient response), 3 (final balance is 0 - never
negative), 4 (movement count is exactly 1), 5 (raw result distribution
recorded, not just a pass/fail).

Server    : 10.4.32-MariaDB
Fixture   : Sku=p1_13_fixture_sku, Id=3 - a separate permanent fixture from
            p1_11_fixture_sku, created idempotently by
            EnsureConcurrencyFixtureProductAsync, so this proof cannot
            disturb the other tests' baseline balance and vice versa.
Mechanism : StockRepository.TryDecrementAsync's conditional UPDATE (ADR-006)
            carries `WHERE ProductId = @productId AND Quantity >= @qty` in
            the same statement as the mutation. Each simultaneous call opens
            its OWN connection and transaction (ConnectionFactory.
            CreateOpenConnectionAsync is called fresh per DecrementAsync
            invocation), so this is genuine concurrent contention at the
            database, serialized by InnoDB row-locking on that UPDATE - not
            by the READ COMMITTED isolation level, which ADR-006's own
            Reasoning says is explicitly not what this design relies on.

Test: StockDecrementTests.Decrement_TwoThenTenSimultaneousRequests_
ExactlyOneSucceedsEachRound (src/tests/Merchandising.Tests.Integration/
StockDecrementTests.vb). Balance is reset to exactly 1.000 before each
round; N calls are fired without awaiting between them so all N are
underway before any is awaited; each attempt is wrapped in its own
try/catch so one unexpected exception cannot hide the outcome of the other
N-1 attempts.
