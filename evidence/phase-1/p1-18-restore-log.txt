SECTION 1 — THE TRAP THAT MAKES AN "ISOLATED" RESTORE NOT ISOLATED
-------------------------------------------------------------------------------
The backups are taken with `mysqldump --databases merchandising`, so every
dump begins:

    CREATE DATABASE /*!32312 IF NOT EXISTS*/ `merchandising` ...
    USE `merchandising`;

Those two lines OVERRIDE `mysql --database=<other>`. Restoring such a dump
"into an isolated database" would silently restore it over the LIVE one
instead. The redirect argument is accepted, appears to work, and does the
opposite of what was asked.

Handled by filtering a COPY of the dump before restoring it:

    source (OFF-HOST, USB): D:/MerchandisingBackups\merchandising-20260822-044039.sql
    database-selection lines removed: 2
    confirm none survived: 0 matches for ^(USE |CREATE DATABASE)

The original dump on the USB is untouched. Only the filtered copy is fed to
mysql.exe.

SECTION 4 — MEASURED TIMING, AND WHAT IT DOES AND DOES NOT COVER
-------------------------------------------------------------------------------
    Restore + verification of a 264,774-byte dump:  0.9 seconds

WHAT THAT NUMBER COVERS: streaming the dump into mysql.exe, and then
verifying — counting rows in five tables and checking all 13 expected tables
exist against information_schema. The clock deliberately stops AFTER
verification, not after the data lands, because "restored" and "confirmed
usable" are different claims and PA-005's target is to a VERIFIED state.

WHAT IT DOES NOT COVER, and this is the honest caveat: stopping the API
Windows Service, starting it again, waiting for /health to answer, and the
operator steps around them. Those are the bulk of a real recovery window and
they need elevation. The full-procedure RTO is therefore NOT recorded yet and
the card's box for it stays unticked.

Against PA-005's demonstrated target of ≤ 15 minutes to verified state, the
database portion consumes 0.9 seconds of the budget — 0.1% of it. The
remaining risk to that target lives entirely in service restart time and
operator hesitation, which is what the rehearsal is for.

SECTION 6 — ONE ACTIVE LOCK, ENFORCED BY THE DATABASE
-------------------------------------------------------------------------------
MariaDB 10.4 has no partial or filtered unique index, so "unique among
unreleased rows only" cannot be expressed directly. Measured on the real
server before the design was committed to:

    CREATE TABLE ... IsActive TINYINT GENERATED ALWAYS AS
        (CASE WHEN ReleasedAtUtc IS NULL THEN 1 ELSE NULL END) PERSISTENT,
        UNIQUE KEY UQ_zz_active (IsActive)

    INSERT a second unreleased row
        -> ERROR 1062 (23000) Duplicate entry '1' for key 'UQ_zz_active'
    UPDATE the first to set ReleasedAtUtc, then INSERT again
        -> accepted; released rows carry IsActive = NULL and do not collide

Why it matters: checking "is a lock already held?" in application code before
inserting is a read-then-write race — two Super Admins acting at the same
moment both read "no lock" and both insert. This is the same reasoning ADR-006
applies to stock balances, and the fix has the same shape: never
read-then-write, let the database refuse it.


SECTION 7 — NO RESTORE ENDPOINT, PROVEN NOT ASSERTED
-------------------------------------------------------------------------------
Spec §15: restore "is not executed as a normal request inside a live API
process that depends on the database". Structural, not stylistic — a restore
replaces the schema the API is mid-query against, and it runs with the
service STOPPED, which an API endpoint cannot arrange for itself.

    404  GET  /api/v1/admin/restore              404  POST same
    404  GET  /api/v1/maintenance/restore        404  POST same
    404  GET  /api/v1/restore                    404  POST same
    404  GET  /restore                           404  POST same
    404  GET  /api/v1/admin/maintenance/restore  404  POST same


SECTION 8 — TWO DEFECTS FOUND BY RUNNING IT
-------------------------------------------------------------------------------
1. MySqlConnector maps CHAR(36) to System.Guid, not String. reader.GetString()
   on CorrelationId threw InvalidCastException, and because it surfaced inside
   middleware it presented as a bare HTTP 500 with a correctly sanitised
   envelope — no hint as to the cause. GetGuid() is the right accessor. Every
   CHAR(36) column in this schema is affected; nothing had READ one back
   before P1-18, which is why it surfaced here first.

2. When mysql.exe rejects an early statement it exits immediately, and the
   rest of the dump streams into a closed pipe. Unhandled, that surfaced as
   "System.IO.IOException: The pipe has been ended" — an unhandled crash that
   told the operator nothing about what mysql actually objected to. The pipe
   error is now caught narrowly, because the real diagnosis is waiting on
   stderr, which the code goes on to read.


WHAT IS STILL OWED
-------------------------------------------------------------------------------
The in-place seven-step rehearsal: enter maintenance -> confirm writes
refused -> STOP THE SERVICE -> restore -> verify -> START THE SERVICE ->
release. Steps 3 and 6 need elevation.

    pwsh ./scripts/restore-rehearsal.ps1 -SuperAdminUsername <admin> -WhatIf
    pwsh ./scripts/restore-rehearsal.ps1 -SuperAdminUsername <admin>

The script times the window, compares it against PA-005's 15-minute target,
and — if verification fails — deliberately LEAVES the system in maintenance
mode. A half-restored database that is open for business is worse than one
that is visibly closed.

It is DESTRUCTIVE: it replaces the live database. -WhatIf walks every step
without executing the destructive ones.
