--- What was built ---
GET /api/v1/products (Products.Read, already gated since P2-07) rewritten
into a two-phase lookup, spec section 10.3: exact Sku/Barcode match first
(ProductRepository.SearchExactAsync); only when that finds nothing does the
original partial Sku/Barcode/Name LIKE search run (SearchPartialAsync). Both
phases LEFT JOIN StockBalances so every hit carries AvailableStock, and both
sort by a whitelisted ProductSortField (name|sku, default name:asc) instead
of a fixed ORDER BY. ADR-018 stands unmodified - Products.Barcode is the one
field this searches; ProductBarcodes is untouched.

--- Note: a fixture-helper bug caught by this suite's own guarantees ---
The first draft of SearchProducts_ReturnsAvailableStockPerHit's fixture
helper (SeedStockDirectlyAsync) called StockRepository.IncrementAsync
directly without writing a matching StockMovements row - exactly the
"balance change without a ledger row" CLAUDE.md section 5 and P4-01's
LedgerReconciliationTests exist to catch. The suite's own assembly-cleanup
reconciliation check failed as designed
(evidence/phase-5/p5-06-product-lookup.txt's own history: ProductId=5190,
Expected=0.000, Actual=12.500). Fixed two ways: (1) SeedStockDirectlyAsync
now writes a compensating StockMovements row in the same transaction, the
same shape AdjustmentTests.SetBalanceAsync already established; (2) the one
already-drifted row from the failing run was healed with a retroactive
StockMovements row (reason "P5-06 ledger repair") so the shared dev
database's ledger integrity holds for every other suite that depends on it.
Confirmed by the full-suite run above being green, including
LedgerReconciliationTests.
