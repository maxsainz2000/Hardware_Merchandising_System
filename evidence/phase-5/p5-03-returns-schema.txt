Design decisions confirmed with the user before implementation:
  - SalesReturns is mutable (INSERT, UPDATE), the same in-place-status
    shape PurchaseOrders/PurchaseReturns/StockCounts/StockAdjustments use -
    not the immutable Sales/SalePayments shape. Inferred from ADR-017
    section 6's self-approval veto, which requires a genuinely distinct
    requester (ReturnedByUserId) and approver (ApprovedByUserId): a return
    within a cashier's permitted scope completes at creation (Status =
    Completed, no approver); one above the configured threshold
    (ExceedsThreshold, captured at request time) is created PendingApproval
    with no stock or refund effect committed yet, and only reaches its
    terminal state through a later, distinct UPDATE by
    SalesReturns.ApproveExceptional.
  - Only three status names (PendingApproval, Completed, Rejected), not
    four. evidence/phase-4/p4-10-adjustments.txt SS0.3 recorded that
    StockAdjustmentStatus's "Approved, not yet Applied" state is never
    actually persisted in practice - ApproveAsync writes the terminal
    status directly, in the same UPDATE that sets the approver. Known
    going in here, so SalesReturnStatus does not name a state nothing will
    ever be observed in.
  - RefundMethod/RefundAmount ("the operational payment-reversal record",
    spec section 11) live on the SalesReturns header, one per return event,
    not per SalesReturnLines row - spec section 11 lists it as one singular
    item alongside "return" and "return lines". Both nullable, filled in
    only once the return reaches Completed, paired by a CHECK the same way
    SalePayments' cash columns are (0011).
  - RestocksItem, not RemovesStock - the sales-return mirror of
    PurchaseReturnLines.RemovesStock, named the other direction and
    matching the name P5-11's own card text already uses.
  - SalesReturnLines does not capture UnitPrice, unlike ReceiptLines/
    PurchaseOrderLines. SaleLines is itself immutable (0011), so a line's
    refund value is safely computed by joining SaleLineId rather than
    re-capturing a value that can never disagree with its source.
  - New Domain enum this card: Merchandising.Domain.Sales.SalesReturnStatus.
