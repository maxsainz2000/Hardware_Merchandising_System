0. The design decision this card required, confirmed before writing code
===============================================================================

Spec section 9 names "returns above a threshold" as a policy-gated operation
but never states the threshold's UNIT. The only precedent (AdjustmentApprovalThreshold,
P4-10) is a quantity. Confirmed with the user rather than decided silently
(the same ADR-017 P3-05 addendum precedent CLAUDE.md section 7 item 4
requires): the threshold is measured against the return's total REFUND VALUE
(money, DECIMAL(19,4)), not the returned quantity. Recorded as
Merchandising.Domain.Sales.SalesReturnThresholdPolicy and a new SystemSettings
key, sales.returnApprovalThreshold (default 5000.0000).

6. Box 6 - SalesReturns.ApproveExceptional reuses ADR-017 section 6, not a new check
===============================================================================

Two real defects were found and fixed while proving this box - both recorded
in docs/adr.md's P5-11 addendum to ADR-017, not just here:

  (a) AuthorizationPolicyRegistration.vb's own header, written at P2-02
      before SalesReturns existed, asserted "SalesReturns.ApproveExceptional
      has no self-approval rule" - false once P5-02's actual role sets are
      checked (CashierAndAbove and AdminAndAbove both include Admin/
      SuperAdmin). Fixed: SalesReturns.ApproveExceptional now carries
      SelfApprovalRequirement, SalesReturn implements IOwnershipResource on
      ReturnedByUserId, and SalesReturnsController.ApproveExceptional
      follows AdjustmentsController.ApproveAdjustment's exact imperative
      shape (role check, then IAuthorizationService.AuthorizeAsync with the
      loaded resource).

  (b) SalesReturnsController.RejectExceptional was first written with the
      SAME declarative <Authorize(Policy:=...)> shape
      AdjustmentsController.RejectAdjustment already uses in production.
      Once the policy carried SelfApprovalRequirement, that shape refused
      EVERY caller 403 regardless of role - ASP.NET Core never supplies an
      IOwnershipResource to a declarative attribute's policy evaluation, so
      the resource-typed handler never runs and the requirement is never
      satisfied. RejectExceptional_PendingReturn_RejectsWithNoStockOrRefundEffect
      caught this immediately (an Admin fixture, unambiguously allowed, got
      403). Fixed the same way as (a)'s controller action: plain
      <Authorize>, role check only, no AuthorizeAsync call (no veto wanted
      for reject). AdjustmentsController.RejectAdjustment almost certainly
      carries the identical latent defect - no test in this codebase drives
      it over real HTTP with an allowed role expecting success - but fixing
      it is out of this card's file list and is recorded in the ADR
      addendum for a future card or standalone fix, not silently patched
      here.
