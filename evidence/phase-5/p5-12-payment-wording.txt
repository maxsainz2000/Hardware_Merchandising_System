1. The denylist test, and what it actually caught
===============================================================================

Two rounds of real friction before the suite was trustworthy, both left in
this file because a wording test that never fired on real content is exactly
as decorative as one that has never fired at all.

ROUND 1 - a VB gotcha, not a design defect. The resource-file helper methods
each declared "Dim path As String = Path.Combine(...)" - VB is case-insensitive,
so the local "path" shadows the System.IO.Path TYPE from the point of its own
declaration, including inside its own initializer. The compiler caught this
immediately and correctly:

  error BC30456: 'Combine' is not a member of 'String'.
  error BC42104: Variable 'path' is used before it has been assigned a value.

Fixed by renaming the locals to "resourcePath" - never shadow a type name the
same method body still needs.

ROUND 2 - the denylist, run for real against the actual committed contract
files, immediately found four matches before any deliberate sabotage:

  SalePaymentResponse.vb: 'Approved' (unnegated) near position 137
  SalePaymentResponse.vb: 'Authorised' (unnegated) near position 149
  SalePaymentResponse.vb: 'Accepted' (unnegated) near position 166
  SalePaymentResponse.vb: 'approved' (unnegated) near position 853

All four are inside that file's own DOC COMMENTS explaining the G-24 rule -
"Status is ALWAYS the literal 'Recorded' - never 'Approved', 'Authorised', or
'Accepted'" - not a string literal a report or a client would ever emit. A
comment describing a banned word necessarily contains it, the same way this
evidence file and the test's own header do. Scanning raw file text without
distinguishing commentary from content would make every doc comment about
G-24 a permanent test failure, which is not what "applied to card/e-wallet
contexts" means.

Fix: PaymentWordingTests.StripCommentary strips whole-line VB comments
(leading ' or ''') and XML/XAML comment blocks (<!-- ... -->) before the
denylist regex runs, so only text a report or a UI actually shows is
scanned. After the fix the real-content scan is clean - see section 3.

===============================================================================

With the suite green, PaymentWording.xaml's CardEWalletRecordedNotice string

Both the denylist scan and the affirmative-wording assertion fired, for the
right reason, on the exact phrase the card names. The label was then reverted
verbatim and the suite re-run:

  dotnet test src/tests/Merchandising.Tests.Unit/Merchandising.Tests.Unit.vbproj --no-build --filter "FullyQualifiedName~PaymentWordingTests"

  Passed!  - Failed: 0, Passed: 5, Skipped: 0, Total: 5, Duration: 42 ms

The corrected text now committed:

  CardEWalletRecordedNotice =
    "Card and e-wallet payments shown here are recorded for this sale only,
     not authorised. This system does not contact any card network,
     e-wallet provider, or bank."

  CardEWalletIntegrationExclusionNotice =
    "No integration exists with a payment terminal, a bank, the cash
     drawer, a weighing scale, a customer display, or a receipt printer."

Round-trip proves three things at once: the denylist fires on an unnegated
occurrence, the corrected wording (which deliberately contains "authorised"
in its negated form) does NOT self-trip the same regex, and the suite
returns clean once the real text is restored. This round-trip is also baked
into the suite itself (Denylist_FiresOnTheExactBadPhrase_AndPassesOnTheCorrectedOne)
so it stays proven on every future run, not just this one.
