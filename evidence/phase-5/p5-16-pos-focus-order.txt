again without a red test.

1. WHAT WAS RUN
===============================================================================

The real Merchandising.POS.MainWindow, with a real MainViewModel signed in
through a stubbed transport - the same StubHttpMessageHandler posture
POSLayoutTests and POSClientTests use, so every line of the client under test
is the real one and only the network is not. The window was positioned at the
origin, sized to the 1366x768 @ 125% work area (1092.8 x 576.0 DIP), shown
and activated. Then, for each of the three tabs: select the tab, let layout
settle, focus the screen's lowest TabIndex, and call

  MoveFocus(New TraversalRequest(FocusNavigationDirection.Next))

repeatedly - the identical traversal the Tab key performs - until focus
returns to a control already visited. Every control authored on the screen is
then reconciled: either it was visited, or the reason WPF skipped it is
named. There is no unexplained skip anywhere below.

The harness is NOT committed, the same division P3-07 made and for the same
reason: it shows and activates a window, which needs an interactive desktop
session, and leaving it in the suite would break every headless run - which
matters because /orchestrate dispatches this suite to box3. The regression
protection lives in POSLayoutTests' four assertions, which show no window.

3. WHAT THIS PROVES, AND WHAT IT DOES NOT
===============================================================================

PROVEN HERE:
  - The window fits the work area, shown, at 1093.0 x 576.0 DIP against the
    1092.8 x 576.0 requested. (The 0.2 DIP is WPF rounding the window to a
    whole device pixel; it is the same figure P3-07 recorded for Procurement.)
  - Every control that receives focus is inside the window bounds - the
    "[on screen]" marker on every line above, none reading OFF SCREEN.
  - Focus visits controls in ascending TabIndex order on all three screens,
    with Sign out (TabIndex 99) last before the cycle wraps to the tab strip.
    The numbers POSLayoutTests asserts statically are therefore the order a
    cashier actually gets.
  - Every authored control is either visited or skipped for a named, correct
    WPF reason - a disabled command, or an empty grid with no focusable cell.
  - The five actions spec section 16 names for the POS mouse-free requirement
    are all reachable in this walk: search (ProductSearchBox 20, Look up 21),
    cart changes (CartQuantityBox 23, Add to cart 24, Remove selected line
    26), payment (PaymentMethodCombo 27, TenderedAmountBox 28), completion
    (Complete sale 29) and session closing (DeclaredCashBox 12, Close session
    13).

NOT PROVEN HERE, and left where the cards already put it:
  - Rendering fidelity at a real 125% DPI - Phase 7's UI pass.
  - Focus VISUALS - whether the focus rectangle reads clearly against each
    background. That is a look question, not a reachability question.
  - Traversal with grids populated and commands enabled. Every grid is empty
    in this fixture, so the six disabled buttons and seven empty grids above
    are skipped by WPF for the reasons named rather than walked. Their
    TabIndex position among their siblings is asserted statically by
    POSLayoutTests.EveryInteractiveControl_HasAUniqueTabIndex_AscendingInReadingOrder;
    a DataGrid's internal cell navigation is DataGrid's own behaviour, not
    this window's authoring. Same limit P3-07 recorded, stated again rather
    than quietly inherited.
