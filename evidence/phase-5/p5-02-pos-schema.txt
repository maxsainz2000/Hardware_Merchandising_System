Design decisions confirmed with the user before implementation:
  - Tables: CashierSessions, Sales, SaleLines, SalePayments (not SaleItems/
    Payments, spec section 12's forward list - the "Lines, not Items"
    precedent 0008/0009/0010 already set, extended to "SalePayments, not
    Payments").
  - No persisted in-progress Sales row: the atomic sale (P5-07) writes a
    Completed header or nothing at all. "Cancelled only before completion"
    (spec section 10.3) is a client-side, pre-API-call fact, never a
    database transition. SaleStatus.Cancelled is declared but driven by no
    card in this phase - the StockCounts/StockAdjustments forward-naming
    precedent (P4-03).
  - Sales and SalePayments (and their child SaleLines) are append-only,
    like Receipts/ReceiptLines - not like PurchaseReturns. No RowVersion,
    no UpdatedAtUtc.
  - CashierSessions carries no running TotalSalesAmount/TransactionCount.
    Every total is a query over committed Sales/SalePayments rows, never a
    maintained counter that could drift from the ledger (ADR-021's
    reconciliation principle, applied here).
  - One open session per cashier enforced now, by the ADR-018 generated-
    column trick (OpenSessionOwner), because P5-04 has no migration file of
    its own to add the index in later.
  - New Domain enums this card: Merchandising.Domain.Sales.PaymentMethod,
    SaleStatus, CashierSessionStatus - the StockCountStatus/
    StockAdjustmentStatus precedent (P4-03): the schema card defines the
    enum, and PosSchemaTests walks [Enum].GetNames against each CHECK.
  - SalePayments.TenderedAmount/ChangeAmount: nullable, cash only, tied to
    Method = 'Cash' by CHECK - for receipt redisplay, mirroring the
    CashTenderResult shape P5-01 built in Domain.
