P3-04 - self-approval denied - focused evidence
Captured 2026-08-27 on this workstation, against the real pinned MariaDB
10.4.32 (XAMPP 8.2.12-0). Spec section 9: a Procurement Officer/Admin
"cannot approve their own purchase order." This file isolates that one claim,
end to end, with two real fixture users (p3_04_fixture_admin_a,
p3_04_fixture_admin_b - both role Admin, so PurchaseOrders.Approve's ROLE
cell is already satisfied for both; the only variable is who requested the
order under approval).

Mechanism (ADR-017 section 6, applied here): PurchaseOrdersController.
ApprovePurchaseOrder loads the order, then calls
IAuthorizationService.AuthorizeAsync(User, order, PurchaseOrders.Approve).
PurchaseOrder now implements IOwnershipResource directly (moved from
Merchandising.Api.Security to Merchandising.Domain.Security this card - see
ADR-017's P3-04 addendum), so SelfApprovalHandler receives a real resource
and compares the authenticated actor's ClaimTypes.NameIdentifier against
RequestedByUserId, calling context.Fail() on a match - an absolute veto, not
merely an unmet requirement.

===============================================================================
2. What the test does, in order
===============================================================================

  1. Log in as admin_a.
  2. POST /api/v1/purchase-orders as admin_a -> 201 Created, Draft.
  3. POST /api/v1/purchase-orders/{id}/submit as admin_a -> 200 OK, Submitted.
  4. POST /api/v1/purchase-orders/{id}/approve as admin_a (the SAME user) ->
     asserted 403 Forbidden, body.ErrorCode == "FORBIDDEN", body.CorrelationId
     non-empty (ADR-014).
  5. Re-read the order directly from the database: Status still "Submitted",
     ApprovedByUserId still NULL, ApprovedAtUtc still NULL - the refusal left
     no partial trace of an approval.
  6. Count AuditLogs rows for this test's own correlation ID, Action =
     "PurchaseOrderApprovalDenied", Result = "Denied" -> exactly 1. The
     refusal itself is audited (spec section 9's privileged-action control:
     actor, timestamp, action, target, result, correlation identifier),
     beyond what P2-04's <AuditRequired> filter strictly forces (that filter
     only forces auditing a 2xx result; this 403 audits by deliberate choice,
     the same precedent LoginFailed/AccountLocked/MaintenanceReleaseRefused
     already set).
