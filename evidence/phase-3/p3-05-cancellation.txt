P3-05 - cancellation and closure rules - acceptance evidence
Captured 2026-08-27 on this workstation, against the real pinned MariaDB
10.4.32 (XAMPP 8.2.12-0), over real HTTP through MerchandisingApiFactory
where the card requires it, and directly against PurchaseOrderService
otherwise. Nothing below is quoted from a design document; every figure is
a measurement.

Endpoints added:
  POST /api/v1/purchase-orders/{id}/cancel   PurchaseOrders.Cancel  [AuditRequired]
  POST /api/v1/purchase-orders/{id}/close    PurchaseOrders.Close   [AuditRequired]

Both routed through P3-01's PurchaseOrderTransitions.CanTransition (ADR-020) -
no new domain logic was needed; the table already had every row this card
needed (Cancel legal from Draft/Submitted/Approved, Close legal only from
PartiallyReceived/FullyReceived, both terminal states already refuse
everything). What P3-05 added is the wiring: two new PolicyRegistry entries
(PurchaseOrders.Cancel, PurchaseOrders.Close - both ProcurementAndAbove,
confirmed with the user before implementing since spec section 13's endpoint
table names neither operation explicitly), two request contracts each
requiring a Reason, two controller actions, and PurchaseOrderService.CancelAsync/
CloseAsync sharing one private TransitionWithReasonAsync helper (both only
ever touch the Status column, unlike Submit/Approve which each own a
distinct extra column).

Matches P3-01's table exactly:
  Cancel:  Draft -> Cancelled (allowed), Submitted -> Cancelled (allowed),
           Approved -> Cancelled (allowed), PartiallyReceived -> REFUSED
           (goods already moved; Close is the only route once receiving has
           started - a receipt already wrote append-only StockMovements).
  Close:   PartiallyReceived -> Closed (allowed), FullyReceived -> Closed
           (allowed), Draft/Submitted/Approved -> REFUSED (nothing has been
           received yet, so there is nothing to close out).

The controller adds no rule of its own: CancelPurchaseOrder/ClosePurchaseOrder
validate only the Reason field's SHAPE (non-empty, <= 500 chars) before
handing the id straight to PurchaseOrderService, which does nothing but ask
CanTransition and act on its answer.

PartiallyReceived/FullyReceived, being unreachable through any live Phase 3
endpoint (Phase 4 owns receiving), are reached in these tests with a direct
SQL UPDATE - fixture setup only, not something any assertion above depends
on for its meaning.

===============================================================================
7. Not owed by this card's done-when boxes, and deliberately not duplicated
===============================================================================

Unlike P3-04, this card's boxes do not ask for a forced-failure/rollback
proof. CancelAsync and CloseAsync share PurchaseOrderService.
TransitionWithReasonAsync - structurally the identical transaction shape
(lock, decide, write, audit, #If DEBUG fault hook, commit) already proved
atomic for ApproveAsync at P3-04
(ApproveAsync_FaultInjectedBeforeCommit_RollsBackStatusAndAuditRows,
evidence/phase-3/p3-04-approval.txt section 5). A second proof of the same
mechanism was judged not worth repeating here.
