5. Status change and audit commit together or not at all (P1-12/P2-08 shape)
===============================================================================

ApproveAsync_FaultInjectedBeforeCommit_RollsBackStatusAndAuditRows: a fault is
thrown inside the same transaction, immediately after the audit insert and
before commit. The unhandled exception propagates out through the enclosing
`Using connection`, whose Dispose() severs the connection and lets MariaDB
roll back whatever was still open (the same mechanism P1-12 proved and
PriceChangeService's own forced-failure test already relies on). Before/after
assertions in the test confirm: Status stays "Submitted" (never "Approved"),
ApprovedByUserId and ApprovedAtUtc stay null, and the AuditLogs row count for
that correlation ID stays zero. Passed [49 ms].

6. Every illegal transition into Submitted/Approved is refused with the
   stable error code PurchaseOrderTransitionErrors.InvalidTransition
===============================================================================

  Approve a Draft order (never submitted)         -> Refused, InvalidTransition
  Submit an already-Submitted order                -> Refused, InvalidTransition
  Submit an Approved order                         -> Refused, InvalidTransition
  Approve an already-Approved order (double-approve) -> Refused, InvalidTransition
  Approve/Submit an unknown order id               -> NotFound (controlled, no exception)

All five asserted directly against PurchaseOrderService.SubmitAsync/ApproveAsync,
complementing PurchaseOrderTransitionTests' 13 pure-table unit tests (P3-01) by
proving the SERVICE actually wires CanTransition end-to-end against committed
rows, not only that the table itself is correct in isolation.
