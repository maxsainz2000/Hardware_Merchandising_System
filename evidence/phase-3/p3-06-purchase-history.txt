===============================================================================
2. Routing: /history does not collide with /{id}
===============================================================================

GET /api/v1/purchase-orders/{id} (P3-03) and GET /api/v1/purchase-orders/history
(this card) sit at the same path depth. ASP.NET Core's attribute routing
prefers a literal segment over a parameter placeholder at the same position
regardless of declaration order - not assumed here, proven directly:
GetPurchaseOrderHistory_OrderedQuantityAndValue_ComputedServerSide (below)
hits GET /purchase-orders/history and gets a 200 with the aggregate shape,
never a 404 or an Id-parse failure from a wrongly-matched {id} route.

Measured directly against the database - three real orders from this
evidence-capture run, using the EXACT SQL shape SearchHistoryAsync runs
(CAST to each column's own storage scale, ADR-004):

$ mysql -u merch_api -p merchandising -e "
    SELECT o.Id, o.OrderNumber, o.Status,
           CAST(COALESCE(SUM(l.OrderedQuantity), 0) AS DECIMAL(19,3)) AS OrderedQuantity,
           CAST(COALESCE(SUM(l.OrderedQuantity * l.PurchaseCost), 0) AS DECIMAL(19,4)) AS OrderedValue,
           CAST(COALESCE(SUM(l.ReceivedQuantity), 0) AS DECIMAL(19,3)) AS ReceivedQuantity,
           CAST(COALESCE(SUM(l.ReceivedQuantity * l.PurchaseCost), 0) AS DECIMAL(19,4)) AS ReceivedValue,
           CAST(COALESCE(SUM(l.OrderedQuantity - l.ReceivedQuantity), 0) AS DECIMAL(19,3)) AS OutstandingQuantity
      FROM purchaseorders o JOIN suppliers s ON s.Id = o.SupplierId
      LEFT JOIN purchaseorderlines l ON l.PurchaseOrderId = o.Id
     WHERE s.Name LIKE 'P3-06 Supplier%'
     GROUP BY o.Id, o.OrderNumber, o.Status ORDER BY o.Id DESC LIMIT 3;"

Scale matches PurchaseOrderHistoryItemResponse exactly: quantities at 3
decimal places, values at 4 - the CAST is what enforces that, not an
accident of MariaDB's default arithmetic widening (an un-CAST SUM on the
same rows returns "1.0000000", 7 decimal places - measured separately,
confirming the CAST is load-bearing, not decorative).

5. Done-when box 3 - date boundaries in the store time zone, stated in the
   response
===============================================================================

StoreTimeZone (Merchandising.Domain) pins Asia/Manila. Measured before any
code depended on it:

  [TimeZoneInfo]::FindSystemTimeZoneById("Asia/Manila")
  -> Id=Asia/Manila, BaseUtcOffset=08:00:00
  AdjustmentRules count: 0, SupportsDaylightSavingTime: False

.NET's ICU-based globalization (default since .NET 5, including Windows)
resolves the IANA id directly; the older NLS-only path would have needed the
Windows id "Singapore Standard Time" instead. Asia/Manila observes no DST,
confirmed rather than assumed, so BaseUtcOffset is the offset for every
calendar date - no seasonal transition to special-case.

$ dotnet test --filter "FullyQualifiedName~GetPurchaseOrderHistory_DateRangeFilter_StoreLocalBoundaries"
  Passed GetPurchaseOrderHistory_DateRangeFilter_StoreLocalBoundaries [289 ms]

An order created "now" is included by a fromDate=toDate=today window,
excluded by a window starting tomorrow, and excluded by a window ending
yesterday - all computed from the actual store-local calendar date at test
time, not a hardcoded date.

$ dotnet test --filter "FullyQualifiedName~GetPurchaseOrderHistory_NoDateFilters_EchoesUnboundedRange"
  Passed GetPurchaseOrderHistory_NoDateFilters_EchoesUnboundedRange [198 ms]

No fromDate/toDate supplied -> response.FromDate and response.ToDate are
both null (never silently defaulted to "today" or any other implicit
window), response.TimeZone is "Asia/Manila" regardless - the zone is always
stated, even when the range is unbounded.
