=== 4. Box 3 (ADR-004.1) - what "before binding" actually proves ===

An over-scale value is refused at the API boundary, BEFORE a connection is
opened. The assertion is the ABSENCE of rows, not the presence of a
correctly-scaled one: MariaDB rounds an over-scale decimal silently (Note
1265, not an error) even under STRICT_TRANS_TABLES, so a stored 12.346 would
look identical whether the guard ran or whether the server rounded it.

  quantity 12.3456 -> 400 VALIDATION_FAILED, field "lines[0].orderedQuantity"
  cost     1.99999 -> 400 VALIDATION_FAILED, field "lines[0].purchaseCost"

Both tests assert PurchaseOrders row count AND IdempotencyKeys row count are
unchanged across the refused request - the key is not even claimed, because
DecimalScaleGuard runs before the transaction begins.


=== 5. FINDING - the isolation level was not what ADR-006 says it was ===

This is the substantive discovery of the card, and it is not confined to
P3-03. It was found by a failing test, measured directly, and is recorded
here because the fix applied is deliberately narrower than the problem.

WHAT WAS MEASURED. Inside a transaction opened by
`connection.BeginTransactionAsync(cancellationToken)`:

  SELECT @@tx_isolation;  ->  REPEATABLE-READ

...despite ConnectionFactory issuing `SET SESSION tx_isolation =
'READ-COMMITTED'` on every connection (P1-05, ADR-006), and despite
ConnectionFactoryTests asserting that session value live.

WHY. MySqlConnector's BeginTransaction sends its own `SET TRANSACTION
ISOLATION LEVEL` for the transaction it opens. That overrides the session
value the connection factory set. The session-level assertion is true and the
transaction-level behaviour is still REPEATABLE READ; nothing in the test
suite compared the two until now.

WHAT IT COST HERE. Under REPEATABLE READ a transaction reads from the
snapshot taken at its first read. PurchaseOrderNumberGenerator's
`SELECT MAX(OrderNumber)` therefore could not see order numbers committed
after this transaction started, while its INSERT (a write, always current)
collided with them. Every retry recomputed the SAME candidate:

  P3-03 DIAG attempt 1 candidate PO-20260827-0040 collided, tx_isolation=REPEATABLE-READ
  P3-03 DIAG attempt 2 candidate PO-20260827-0040 collided, tx_isolation=REPEATABLE-READ
  P3-03 DIAG attempt 3 candidate PO-20260827-0040 collided, tx_isolation=REPEATABLE-READ
  ... (identical candidate every attempt, until the retry bound was exhausted)

Ten concurrent creates with distinct keys failed nine of ten requests with a
409. Raising the retry bound did NOT fix it - the bound was never the cause.

THE FIX APPLIED. PurchaseOrderService now passes the level explicitly:

  Await connection.BeginTransactionAsync(IsolationLevel.ReadCommitted, cancellationToken)

After it, the same ten-way test passes and produces ten distinct order
numbers (section 3 above: 97 orders, 97 distinct numbers).

WHAT IS DELIBERATELY NOT FIXED, AND IS NOW OPEN WORK. Every other
BeginTransaction call site in the API still opens a REPEATABLE READ
transaction - StockService, PriceChangeService, ProductLifecycleService,
SupplierLifecycleService, SuppliersController, ProductsController,
MaintenanceController. None of their tests fail today: their correctness
rests on InnoDB row locking on a conditional UPDATE (ADR-006's own stated
mechanism, P1-11/P1-13), and a locking read always sees the latest committed
row regardless of isolation level. So this is a divergence between ADR-006's
text and the running system, NOT a known-broken guarantee.

It is left open rather than fixed here because changing the isolation level
of the stock decrement, the price change and the maintenance lock is a change
to three proven, evidenced Phase 1/Phase 2 mechanisms, and each owns its own
tests and evidence. That is a card, not a footnote in this one.
CLAUDE.md section 6.2 already warns exactly this ("the default isolation
level is REPEATABLE-READ ... set it explicitly. Never assume it"); what is
new is that setting it on the SESSION is not sufficient, and ADR-006 should
say so.


=== 6. Spec section 13 list contract, as defined and asserted ===

  page       default 1;  below 1 clamped to 1
  pageSize   default 25; below 1 clamped to 25; above 100 clamped DOWN to 100
  maxPageSize 100, echoed in the response body
  sort       default createdAt:desc; whitelist {createdAt, orderNumber,
             status}, each :asc or :desc; anything else 400 with field "sort"
  filters    supplierId, status; an unknown status is 400 with field
             "status", never silently ignored

Asserted: pageSize=5000 returns pageSize 100; page=-4&pageSize=0 returns
page 1 / pageSize 25; sort=rowVersion:asc is refused 400; pages 1/2/3 at
pageSize 2 over 5 orders return 2/2/1 items with 5 distinct ids and no
overlap; TotalCount is the whole result set, not the page.

Sorting cannot be injected by construction, not merely by validation:
PurchaseOrderRepository.SearchAsync takes a PurchaseOrderSortField enum, so
no caller can hand it a column name at all.

DATE-BOUNDARY FILTERING IS DELIBERATELY ABSENT and belongs to P3-06, which
owns store-time-zone (Asia/Manila) boundaries against UTC storage. The
PO-yyyyMMdd-NNNN order number embeds a UTC date as a LABEL; it must not be
read to decide what store-local day an order was raised.


=== 7. Stable error codes introduced ===

  VALIDATION_FAILED          400  with field-level detail (ADR-014)
  SUPPLIER_INACTIVE          400  order raised against a deactivated supplier
  PRODUCT_INACTIVE           400  deactivated product newly ordered (spec 10.2)
  PURCHASE_ORDER_NOT_FOUND   404  unknown order id, controlled, no leak

Every error body carries a correlation ID; none carries a stack trace, SQL
text, connection string, or environment detail.
