WHY THIS FILE EXISTS.

At the Phase 3 gate this box was the one open item on the card, deferred to
the Phase 7 UI pass. The deferral rested on a sentence in
p3-07-procurement-client.txt which its own arithmetic refuted:

  "the window's default size (1024x680, MinWidth 960, MinHeight 620) fits
   inside a 1366x768 desktop at 125% scaling (effective ~1093x614 minus
   taskbar) with room to spare"

680 and 620 are both larger than the 614 the same clause computes. The
figures were right and the conclusion drawn from them was wrong. MinHeight
is the value that mattered: a window whose MINIMUM exceeds the work area
cannot be dragged or resized into it, so the status bar along the bottom
would have been permanently off-screen on every 1366x768 demo laptop.

WHAT WAS CHANGED (P3-07a).

  src/Merchandising.Procurement/MainWindow.xaml
    Height    680 -> 560        MinHeight 620 -> 520      (Width/MinWidth unchanged)
    New Order tab, row 0:  Height="260"  ->  Height="1.4*" MinHeight="170"
    New Order tab, row 1:  Height="*"    ->  Height="1*"   MinHeight="120"

The second change is not cosmetic. A fixed 260 DIP row cannot give way on a
short desktop; measured at the corrected MinHeight it left the Lines grid at
0.0 DIP - laid out, focusable, and invisible. See section 3.

===============================================================================
1. THE BUDGET, AND WHY NO DISPLAY SETTING WAS CHANGED
===============================================================================

WPF lays out in device-independent pixels: 1 DIP = 1/96". A display's scaling
factor converts DIP to physical pixels - it does not change the layout. So:

  screen        1366 / 1.25  x  768 / 1.25   =  1092.8 x 614.4 DIP
  taskbar       48 physical px / 1.25        =      38.4 DIP
  WORK AREA     1092.8 x 576.0 DIP

Every Width/Height/MinWidth/MinHeight in MainWindow.xaml is already in those
units, so constraining layout to that DIP budget is the identical layout
problem the real display poses. That is what makes this measurable on a
1920x1200 @ 100% workstation without setting the OS to 1366x768 @ 125%.

NOT claimed by this file: rendering fidelity at 125% - glyph hinting, image
crispness, hairline border rounding. Those need the real display and are the
Phase 7 UI pass's subject. The claim here is fit, reachability and order.

  declared value   budget     verdict
  --------------   --------   -------
  MinHeight  520    576.0     fits
  Height     560    576.0     fits
  MinWidth   960   1092.8     fits
  Width     1024   1092.8     fits

5. HOW SECTION 4 WAS PRODUCED, AND WHAT IT DOES AND DOES NOT PROVE
===============================================================================

A throwaway MSTest harness (TempFocusCapture) constructed MainWindow, gave it
a MainViewModel signed in through a stubbed transport - the same
StubHttpMessageHandler posture ProcurementClientTests uses, so every line of
the client under test is the real one - sized the window to 1092.8 x 576.0
DIP, showed and activated it, then for each tab focused the lowest TabIndex
and called MoveFocus repeatedly until the cycle repeated.

The harness is NOT committed. It shows a window and activates it, which needs
an interactive desktop session; leaving it in the suite would break every
headless run for the sake of a capture that only needs making once. This is
the same division P3-07 already used: the live click-through
(p3-07-live-clickthrough-2026-08-28/) is a captured artifact, while the view
model rules that must not regress are suite tests. The regression protection
for THIS box lives in ProcurementLayoutTests, section 2.

PROVEN HERE:
  - The window fits the work area, shown, at 1093.0 x 576.0 DIP.
  - Every control that receives focus is inside the window bounds - the
    "[on screen]" marker on every line of section 4, none reading OFF SCREEN.
  - Focus visits controls in ascending TabIndex order on all four screens,
    with Sign out (TabIndex 99) last before the cycle wraps to the tab strip.
  - Every authored control is either visited or skipped for a named, correct
    WPF reason (a disabled command, or an empty grid with no focusable cell).

NOT PROVEN HERE, and left to the Phase 7 UI pass as the card intends:
  - Rendering fidelity at a real 125% DPI.
  - Focus VISUALS - whether the focus rectangle is clearly visible against
    each background. That is a look question, not a reachability question.
  - Traversal with grids populated. Every grid was empty in this fixture, so
    the four grids' internal cell navigation was not walked. Their TabIndex
    position among their siblings is asserted statically in section 2's third
    test; their internal navigation is DataGrid's own behaviour, not this
    window's authoring.
