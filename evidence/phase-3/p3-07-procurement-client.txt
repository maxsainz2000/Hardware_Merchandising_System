2. Two real defects, found only by launching the actual app
===============================================================================

CLAUDE.md requires a UI change to actually be run, not just unit-tested, and
this card is the reason why. Both of these passed 41/41 unit tests and both
crashed or misbehaved the first time the real window opened.

Defect A - startup crash, every screen. WPF's <Run Text="{Binding X}"/>
defaults to a TwoWay binding (Run supports RichTextBox editing), and every
read-only status property (CorrelationId, SelectedSupplierDisplay,
AppliedTimeZone, TotalCount) bound that way. First launch:

  System.InvalidOperationException: A TwoWay or OneWayToSource binding
  cannot work on the read-only property 'CorrelationId' of type
  'Merchandising.Procurement.ViewModels.SupplierBrowseViewModel'.
    at System.Windows.Window.ShowHelper(Object booleanBox)
    ... Merchandising.Procurement.Application.Main()

  (captured live via Get-WinEvent -LogName Application, .NET Runtime
  event 1026, two occurrences, both before the fix)

Fixed by adding Mode=OneWay to every <Run Text="{Binding ...}"/> in
MainWindow.xaml (8 occurrences). Rebuilt, relaunched: no crash, window opens
and stays responsive (Get-Process ... | Select MainWindowTitle, Responding
-> "Merchandising - Procurement", True).

Defect B - a transition's own refusal message got silently erased.
PurchaseOrderListViewModel.ApplyTransitionAsync originally called
Await RefreshAsync() unconditionally after every submit/approve/cancel
attempt - including a FAILED one. RefreshAsync's own success path
overwrites StatusMessage/ResultText/CorrelationId with "{N} order(s)
found.", so a 403 self-approval refusal (or any other refusal) was shown
for a single frame and then replaced by the list's own "N found" message -
exactly the "hides the correlation ID" failure this card's own Done-when
box rules out, just caused by the VIEW MODEL rather than by the server.

Caught by ApproveAsync_SelfApprovalRefusalSurfacesVerbatim
(ProcurementClientTests.vb) before it ever reached the live app: the test
asserted LastCallFailed/StatusMessage/ResultText/CorrelationId immediately
after ApproveAsync() and failed because RefreshAsync's own success reset
them. Fixed by extracting ReloadOrdersListQuietlyAsync, called only on a
SUCCESSFUL transition, and never touching the status/result/correlation
fields the caller just set. Re-ran the same test: green (see section 1).

A second, related fix in the same pass: SelectedOrderSummary's setter
originally fired an async-void LoadDetailAsync as a side effect - a race
with whoever just set the property (the same class of bug ADR-017's
AsyncLocal note already describes for this codebase, just in a different
place). Replaced with a public LoadSelectedOrderDetailAsync the DataGrid's
SelectionChanged handler in MainWindow.xaml.vb awaits explicitly, and
RefreshAsync now awaits it too rather than firing it unobserved.


===============================================================================
3. An unrelated, pre-existing environment defect, found and fixed along the
   way (not a P3-07 change, recorded here because fixing it was required to
   finish this card's own live verification)
===============================================================================

The running MerchandisingApi Windows Service was six days stale (built
2026-08-22, before P2-07 Products, P2-10 Suppliers, or any Phase 3 endpoint
existed). GET /api/v1/suppliers and /api/v1/products both 404'd - confirmed
with curl directly against the service, independent of this client:

  $ curl -sk -i "https://MERCH-HOST:8443/api/v1/suppliers?..." -H "Authorization: Bearer ..."
  HTTP/1.1 404 Not Found

Redeployed with the user's explicit confirmation (scripts/publish-release.ps1
-Component Api -Mode SelfContained, then the elevated scripts/install-service.ps1).
First redeploy attempt published into artifacts/publish/Api-sc (inside the
repo) and the service then failed to start - "Cannot start service" - because
that directory's ACL grants only the interactive user account plus
Administrators/SYSTEM, with no BUILTIN\Users or Authenticated Users entry, so
the virtual service account NT SERVICE\MerchandisingApi could not read its
own executable:

  $ icacls "...\artifacts\publish\Api-sc"
  NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
  BUILTIN\Administrators:(I)(OI)(CI)(F)
  LAPTOP-3HH6OHHE\Admin:(I)(OI)(CI)(F)          <- no Users/Authenticated Users

Republished to C:\MerchandisingService\Api-sc instead (the original working
deployment's own location, whose parent directory already carries
BUILTIN\Users:(RX) and Authenticated Users:(M), inherited correctly onto the
new files), then re-ran install-service.ps1 pointing there. Service started
cleanly:

  $ curl -sk https://MERCH-HOST:8443/health
  {"status":"ok","version":"0.1.0","utcTime":"..."}
  $ curl -sk -i "https://MERCH-HOST:8443/api/v1/suppliers"
  HTTP/1.1 401 Unauthorized        <- no longer 404: the route now exists

This is scripts/install-service.ps1's own documented warning ("Publish
somewhere else for a real install") turning out to have a second, sharper
reason than file-overwrite: the ACL, not just the risk of a later build
clobbering a running service. Worth a line in a future hardening pass; not
otherwise a P3-07 change.

5. What this card's Done-when boxes ask for, and where each is satisfied
===============================================================================

- Login, supplier browse, order create/submit/approve/cancel and history all
  work against the running API -> section 4, all nine steps performed live.
- Guardrail G-B holds (no Infrastructure/MySqlConnector/DB package reference,
  no connection string) -> section 1, G-B pass, unchanged from every prior
  card; ClientCommon and Procurement still reference only Contracts.
- Server-side refusals surface the API's own message/code, never hide the
  correlation ID -> section 4.1 (wrong credentials), 4.6 (wrong role), and
  ProcurementClientTests' two rejection tests (section 1).
- Client-side validation is for usability only, every rule re-checked
  server-side -> AddLine/CreateOrderAsync/CancelAsync each check only "is
  this a plausible number" / "is a reason present" before sending; every
  actual business rule (supplier/product existence and active state,
  quantity/cost scale, the status machine, the self-approval veto) is
  decided by PurchaseOrdersController and PurchaseOrderService, never
  duplicated in a view model.
- Keyboard navigation and focus order at 1366x768 and 125% scaling -> every
  interactive control carries an explicit TabIndex in visit order per screen
  (MainWindow.xaml).
