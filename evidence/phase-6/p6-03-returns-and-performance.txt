5. WHAT THE TWO REPORTS QUERY, AND HOW FAN-OUT WAS AVOIDED
---------------------------------------------------------------------

Returns and cancellations (ReportRepository.GetReturnsAndCancellationsAsync):
a FLAT per-line listing - SalesReturnLines JOIN SalesReturns JOIN Products
JOIN Users (actor) LEFT JOIN Users (approver). No GROUP BY anywhere, so this
is a plain multi-table join, not the pre-aggregated-subquery shape P6-02's
ReportRepository header requires for a SUM() over more than one one-to-many
relation - that concern does not apply to a row-per-line listing.

Product performance (ReportRepository.GetProductPerformanceAsync): the
SAME shape GetSalesByProductAsync (P6-02) already establishes - Products
JOIN a pre-aggregated "sold" subquery (SaleLines/Sales, Completed, in
window) LEFT JOIN a pre-aggregated "returned" subquery (SalesReturnLines/
SalesReturns/SaleLines, Completed, in window) - extended here so the
returned subquery ALSO computes ReturnedValue and ReturnedCostBasis (both
via the same join to SaleLines.UnitPrice/Cost SalesReturnLineResponse's own
header already establishes as the captured, never-recomputed source). A
THIRD join, to StockBalances, is added directly and unaggregated - safe
because StockBalances is 1:1 per product, never one-to-many, so it cannot
fan out anything the first two subqueries already collapsed to one row per
product. That join deliberately carries no date predicate at all - see
section 7 below.

8. A LATENT FRAGILITY FOUND AND FIXED DURING THIS CARD
    (in P6-02's own, already-committed test file)
---------------------------------------------------------------------

The FIRST full-suite run attempted for this card (486 tests, up from
P6-02's 480) failed 4 - not in this card's own new file, but in
SalesReportsTests.vb (P6-02): SalesByProduct_Reconciles_
AgainstSalesDetailEndpoint and SalesByProduct_CostChangedAfterSale_
CapturedCostBasisUnmoved, plus two of THIS card's own new product-
performance tests.

Root cause, confirmed directly against the shared database rather than
guessed: every one of these fixture tests creates a brand-new Products row
with a freshly-generated random SKU on every run, and this session alone
had by then run the full suite and these specific test classes many times
over the course of Phase 6. A direct query against the live database
confirmed 191 DISTINCT products had a completed sale line dated "today" -
comfortably past the by-product/product-performance reports' own
pageSize=100 ceiling (P3-03's inherited contract). Both failing tests
fetched only PAGE 1 of the by-product report and called
.Single(Function(i) i.ProductId = productId) against it - a call that fails
whenever the fixture product's name ("P6-02 Fixture Product"/"P6-03
Fixture Product", identical across every run of a given test file, so
products from the SAME file all sort adjacently) happens to land past page
1's ordinal ProductName-ascending cutoff, which by the time of this card's
first run it usually did. By-cashier tests never showed this, because their
fixture cashier USERNAME is reused across runs (not regenerated), so the
distinct-cashier count for "today" was a stable 27, never close to 100.

This bug pre-dates this card (P6-02 shipped it, ticked green, because the
database had not yet grown past the threshold) and is not something this
card's own Done-when boxes name - but "integration suite green" (both this
card's own box and, retroactively, P6-02's already-ticked one) cannot be
honestly claimed while it stands, so it was fixed here rather than deferred.

FIX: three "fetch every page" helpers were added -
SalesReportsTests.FetchAllByProductAsync (P6-02's file, fixing its own two
affected tests), and this card's own
ReturnsAndPerformanceReportsTests.FetchAllReturnsAndCancellationsAsync /
FetchAllProductPerformanceAsync / FetchAllStockAsync - the identical
"page until TotalCount is reached" shape FetchAllSalesAsync/
FetchAllReturnsAsync already use for detail-endpoint sums, now applied to
the REPORT'S OWN paginated response too wherever a test needs to find one
specific fixture row rather than sum everything. Not fixed, and explicitly
out of this card's scope: ReportRepository's by-product/by-cashier/product-
performance ORDER BY clauses carry no secondary tie-break column (unlike
SalesReturnRepository.SearchAsync's ReturnedAtUtc-then-Id shape, added at
this same card for the new detail endpoint) - two consecutive full-suite
runs (section 7d) both went green, so this was not chased further here,
but it is a real, named gap for a future card to close if a genuine
concurrent-pagination flake is ever observed.
