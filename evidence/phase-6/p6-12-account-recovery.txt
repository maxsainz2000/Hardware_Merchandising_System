P6-12 / CARRY-01 — reset-password and unlock-user on the Maintenance CLI
==========================================================================
Spec section 23 (gap register row G-19, "account recovery"). Decides ADR-028. Surfaced
at the Phase 2 gate and carried through Phases 2 -> 3 -> 4 -> 5; closed here.
Machine: this laptop, doubling as MERCH-HOST (API service already running at
https://127.0.0.1:8443, published before this task).

DONE-WHEN BOXES, MAPPED TO PROOF
---------------------------------
1. reset-password sets a new password through the same hashing path create-user
   uses, never a second implementation, never a plaintext column.
   -> ResetPasswordCommand.vb calls the SAME Merchandising.Infrastructure.Security.
      PasswordHashingService.HashPassword CreateUserCommand.vb already calls.
      Proven live in PART 2 below (old password rejected, new password accepted)
      and by AccountRecoveryTests.ResetPassword_ValidTarget_ChangesPasswordAndAuditsIt.

2. unlock-user clears LockedUntilUtc and the failed-attempt counter, distinct from
   reset-password because the two failures are different.
   -> UnlockUserCommand.vb reuses UserRepository.RecordSuccessfulLoginAsync's existing
      clear-lockout UPDATE (given an Optional transaction parameter, P1-11's own
      pattern) rather than a second copy of that SQL. Proven live in PART 2 (a real
      423-locked account, unlocked, login succeeds again) and by
      AccountRecoveryTests.UnlockUser_LockedAccount_ClearsLockoutAndAuditsIt.

3. Both write an AuditLogs row naming the operator and the target account.
   -> Proven live in PART 2 by querying AuditLogs directly after both commands ran
      against real accounts, and by AccountRecoveryTests' before/after audit-count
      deltas (ResetPassword_ValidTarget_ChangesPasswordAndAuditsIt,
      UnlockUser_LockedAccount_ClearsLockoutAndAuditsIt).

4. Both run ONLY as the maintenance identity on the host, never through an API route
   - asserted by confirming no route reaches them.
   -> AccountRecoveryTests.NoHttpRoute_ReachesResetPasswordOrUnlockUser enumerates
      every ControllerActionDescriptor in the API assembly (18 controllers) and fails
      if any action name or route template names either command, or if a
      UsersController exists at all. Passes because there is no such controller
      (ADR-017 section 4).

5. The user guide documents both, in the words an operator would search for
   ("forgot password", "locked out").
   -> docs/user-guide.md, section "Account recovery", subsections "I forgot my
      password" and "My account is locked out" (those exact phrases, as headings).

6. ADR-028 records why recovery is CLI-only and what that costs on demo day.
   -> docs/adr.md, ADR-028 (inserted before "Template for new entries").

A REAL MISTAKE MADE WHILE CAPTURING THIS EVIDENCE, RECORDED RATHER THAN QUIETLY FIXED
-----------------------------------------------------------------------------------------
The plan was to delete both throwaway demo accounts after capturing their transcript,
the same disposable-fixture cleanup SeedCommandTests already uses for its own fixture
rows. That plan was wrong for these two specifically: by the time cleanup ran, both
accounts were named as ActorUserId on real AuditLogs rows (the ResetPassword/UnlockUser
rows above), and AuditLogs is append-only with a foreign key to Users - deleting the
Users row would require deleting the audit trail first, which CLAUDE.md section 5
forbids outright. The DELETE statements for UserRoles and Sessions had already run
(autocommit, no wrapping transaction) before the Users DELETE failed on the foreign-key
constraint, leaving both accounts orphaned - present in Users, absent from UserRoles.
Fixed by re-inserting the same role assignment each account was given at creation
(UserId 20490 -> RoleId 1 SuperAdmin, UserId 20491 -> RoleId 5 Cashier), confirmed by
re-querying UserRoles joined to Roles. Both accounts now stay as permanent rows, the
same category AuthenticationTests' and AuthorizationMatrixTests' own fixture accounts
already occupy for the identical reason - this is the same lesson those suites'
comments already state, re-learned by hand rather than read: "AuditLogs.ActorUserId is
a foreign key to Users, and AuditLogs is append-only - a test/demo account is never
scratch data to delete." The automated suite's own fixtures (p6_12_fixture_operator,
p6_12_fixture_target, created idempotently by AccountRecoveryTests.SetUpAsync) were
never at risk - only these two manually-created demo accounts.
