1. Scope
-------------------------------------------------------------------

Spec section 14 rows 8-11, per docs/report-specification.md (the P6-01
document Track B cards cite instead of re-deciding these questions) - the
last four of the twelve reports:

  - Current stock report
    GET /api/v1/reports/inventory/current-stock
    Product, category, active state, current quantity, reorder level, and
    stock status. Point-in-time snapshot - no date parameter, matching
    GET /api/v1/inventory/stock's own contract. ReturnsTreatment = Excluded.

  - Low-stock report
    GET /api/v1/reports/inventory/low-stock
    Active products at or below reorder level, with current quantity and
    reorder level. ReturnsTreatment = Excluded.

  - Stock movement report
    GET /api/v1/reports/inventory/stock-movements
    Movement source, product, delta, before/after quantity, user, time,
    reason, and correlation identifier. ReturnsTreatment = Included.

  - Stock-adjustment report
    GET /api/v1/reports/inventory/stock-adjustments
    Count/adjustment, variance, reason, requestor, approver, result, and
    stock effect. ReturnsTreatment = Excluded.

Per docs/report-specification.md section 7's table, all four reconcile
against the SAME two existing detail endpoints: GET /api/v1/inventory/stock
and GET /api/v1/inventory/stock/movements (both P4-11). No new detail
endpoint was needed for this card, unlike P6-02/P6-03.

Design decisions made in this card, not re-litigated from that document:

  - CURRENT STOCK is a genuinely independent SQL query (joins Categories,
    which StockRepository.SearchStockAsync has no reason to), reconciled
    against /api/v1/inventory/stock's Quantity/ReorderLevel per product -
    a real two-independent-code-paths proof (ADR-023), not the same query
    called twice.

  - LOW STOCK calls StockRepository.SearchLowStockAsync DIRECTLY through
    ReportService.GetLowStockReportAsync - P4-11's own threshold comparison,
    never restated as a second WHERE clause (this card's own Done-when box).
    Because the report and GET /api/v1/inventory/low-stock would therefore
    be the identical query, the reconciliation test compares the report's
    row set against GET /api/v1/inventory/stock filtered CLIENT-SIDE by the
    same threshold (Quantity <= ReorderLevel) instead - a genuine second
    computation of the filter, never the report's own query run twice.

  - STOCK MOVEMENT is a new query, structurally close to
    StockRepository.SearchMovementsAsync but with an OPTIONAL productId
    (the existing endpoint requires one) - needed for this card's own
    Done-when box: "current stock and the movement report agree with each
    other for EVERY product," not one product at a time. Reconciled against
    the existing, already-shipped GET /api/v1/inventory/stock/movements for
    one product at a time (still two independent code paths - a NEW query
    compared to an EXISTING one, the same shape P6-04 used for purchase
    orders vs. goods receiving).

  - STOCK ADJUSTMENT is the FIRST GET route StockAdjustments has ever had
    (AdjustmentsController only ever added POST routes at P4-10, confirmed
    by inspection). "Result" is Status, read and echoed verbatim (ADR-020's
    sibling status machine, never re-decided here). "Stock effect" is a new
    derived StockEffectApplied boolean (True only when Status = "Applied"),
    because StockAdjustments carries no MovementId column - the actual
    quantity effect, when applied, IS QuantityVariance itself. Reconciled by
    matching an Applied adjustment's QuantityVariance against the exact
    StockMovements row it produced (found via CorrelationId, through the
    stock movement report) - two different source tables, never the same
    query twice, and the Pending case is proven to leave no matching
    movement row at all.

5. Notes
-------------------------------------------------------------------

- SHARED, MUTABLE SYSTEM SETTING HAZARD, HANDLED. inventory.adjustmentThreshold
  (SystemSettings) is shared state that another test class in this suite
  (AdjustmentTests.vb) writes and does not restore. The first run of this
  card's tests failed against fixed literal variances for exactly this
  reason - a prior test class had left the threshold below 8.000, so
  fixtures expecting "Applied" (below threshold) got "Pending" instead.
  Fixed by pinning inventory.adjustmentThreshold to a known value
  (SystemSettingsRepository.UpsertAsync, the identical mechanism
  AdjustmentTests.vb's own SetThresholdAsync uses) in this class's own
  TestInitialize - safe because the assembly carries <DoNotParallelize>
  (AdjustmentTests.vb's own header, ADR-009.2), so no other test class can
  be running concurrently and observe the pinned value mid-test.

- StockAdjustments carries no MovementId or CorrelationId column - an
  adjustment's stock effect is traced to its StockMovements row entirely by
  CorrelationId, which IS available because this card's own fixtures call
  AdjustmentService.RequestAsync directly (not through HTTP) and therefore
  control and know the correlation id passed in, the same fixture style
  P6-04 established for calling PurchaseOrderService/ReceivingService
  directly.

- StockStatus ("OutOfStock"/"Low"/"Normal") and StockEffectApplied are both
  derived in ReportService, never stored - the same layering
  GetProductPerformanceAsync's MarginEstimate already established at P6-03
  for a report's one genuinely new derived figure.
