===========================================================
Spec section 23 (gap register row G-16, "no mechanism in this repository could detect
a stale deployment"). Decides ADR-027. Machine: this laptop, doubling as MERCH-HOST.

THIS FILE IS WRITTEN IN TWO PARTS BY CONSTRUCTION, NOT BY ACCIDENT.
--------------------------------------------------------------------
The card's own acceptance test ("run the comparison, make a source commit without
redeploying, confirm the check goes red") requires a real commit boundary to exist
between two of its steps. Part 1 below covers everything provable before the P6-10
commit exists. Part 2, appended immediately after that commit in a short follow-up

FIRST and watched to fail for the right reason before HealthController.vb changed —
CollectionAssert.AreEquivalent reported "Expected:<5>. Actual:<3>." against the

3. THE PRE-EXISTING STALE DEPLOYMENT — read before any of this card's code existed
-------------------------------------------------------------------------------------
Before implementing anything, the ALREADY-RUNNING MerchandisingApi service on this
machine (published before this phase, serving since the P0-05/P1-16 line of work) was
checked with the new -CheckOnly switch, run against the OLD (pre-P6-10) health payload
which has no commitSha field at all:

    FAIL STALE DEPLOYMENT: the running service was published from a different commit
    than the current tree.

This is exactly the defect CARRY-05 names: a real, already-present stale deployment,
undetected by every test in the 505-test integration suite (which builds its host
in-process, from the current tree, and therefore cannot see a separately-deployed
process at all — see ADR-027 point 4), caught the moment a mechanism actually looked
at the two things that matter: the tree's HEAD and the running process's own identity.

This closes boxes 1, 2, 4 and 5 of the card: the endpoint carries a publish-time
commit and timestamp (never re-read from the tree at request time — the deployed
process above kept reporting 721f2ffe... across multiple checks while the working
tree already held every uncommitted P6-10 change, which is exactly the "does not
always agree with itself" property required); a script (install-service.ps1
-CheckOnly) compares it against git rev-parse HEAD and fails loudly, with both values
printed, when they differ (step 3 above); the same comparison runs automatically as
the last step of a normal install and would have refused to report success on a
mismatch (nothing to show here since this install was not stale — Part 2 exercises
the refusal path indirectly by showing the identical function goes red the moment the
tree moves without a matching install); and the payload leaks nothing beyond commit
and timestamp (test in section 2).
